## PART A — Merge queue mechanics

### A1. How GitHub constructs merge groups

**Temporary branches and commits.** "A merge queue creates temporary branches with a special prefix to validate pull request changes. When a pull request is added to the merge queue, the changes in the pull request are grouped into a `merge_group` with the latest version of the `base_branch` as well as changes from pull requests ahead of it in the queue." Third-party CI must run on branches "that begin with the special prefix `gh-readonly-queue/{base_branch}`. These are the temporary branches that are created on your behalf by a merge queue and contain a different `sha` from the pull request." (Managing a merge queue, docs main 2026-09-19.) The webhook payload describes the group as `head_sha` ("The SHA of the merge group"), `head_ref` ("The full ref of the merge group"), `base_sha` ("The SHA of the merge group's parent commit"), `base_ref`, and `head_commit` (OpenAPI `merge-group` schema).

The worked examples in the doc make the cumulative structure explicit: PR #1's temporary branch contains base + PR1; PR #2's temporary branch contains base + PR1 + PR2. When both are green, "the temporary branch `main/pr-2` will be merged in to the target branch" — i.e. **the merge to the base branch is a fast-forward-style adoption of the last green group commit, not a re-merge of each PR**.

**Merge method.** The rule setting "Merge method: Method to use when merging changes from pull requests" (merge / squash / rebase). GraphQL exposes it as `MergeQueueConfiguration.mergeMethod: PullRequestMergeMethod`. Note that with rebase or squash, the SHAs that land on the base branch are created by the queue; the PR head SHA itself never becomes part of base history (see also "Rebase and merge will always update the committer information and create new commit SHAs", Merging a pull request doc).

**Group sizing and timing.** Documented settings (Available rules for rulesets → Require merge queue; Managing a merge queue):

| Setting | Doc wording | GraphQL field |
|---|---|---|
| Build concurrency (1–100) | "Limit the number of queued pull requests requesting checks and workflow runs at the same time... controls when merge queue dispatches the `merge_group.checks_requested` webhook event" | `maximumEntriesToBuild` |
| Minimum/maximum group size (1–100) | "The number of pull requests that will be merged together in a group" | `minimumEntriesToMerge`, `maximumEntriesToMerge` |
| Wait time to meet minimum group size (minutes) | "After this time has elapsed, the minimum group size will be ignored and a smaller group will be merged" | `minimumEntriesToMergeWaitTime` |
| Status check timeout (minutes) | "After this much time has elapsed, checks that have not reported a conclusion will be assumed to have failed" | `checkResponseTimeout` |
| Require all queue entries to pass required checks | see below | `mergingStrategy` |

Important nuance from the doc: "Merge limits do not combine `merge_group` **builds**. Merge limits only affect merges to the base branch once one or more `merge_group` has satisfied build checks." So group size controls how many PRs land in one base-branch update; it does not change the one-temporary-branch-per-entry build model.

**Merging strategy (ALLGREEN vs HEADGREEN).** "Require all queue entries to pass required checks: When this setting is enabled, each item in the merge group must pass all required checks. When this setting is disabled, only the commit at the head of the merge group, i.e. the commit containing changes from all of the pull requests in the group, must pass its required checks to merge." The older doc phrasing ("Only merge non-failing pull requests") adds: "Pull requests that have failed required checks can be added to a group as long as the last pull request in the group has passed required checks... useful if you have intermittent test failures." GraphQL: `MergeQueueMergingStrategy { ALLGREEN "Entries only allowed to merge if they are passing", HEADGREEN "Failing Entires are allowed to merge if they are with a passing entry" }` and `MergeQueueGroupingStrategy { ALLGREEN, HEADGREEN }`.

**Implication for "what green means":** under HEADGREEN, an individual PR can be merged into base while *its own* merge-group commit had failing required checks; the only guarantee is that the *cumulative* head commit passed. A receipt that binds evidence to "the candidate that was actually tested and merged" must therefore record the merging strategy and which group commit's checks satisfied the merge.

**"Required status checks" for a merge group.** "Merge queue and pull requests checks are coupled and configured under branch protection rules or rulesets" — there is one list of required check names; the queue waits for those same names to be reported on the merge-group `head_sha`. "A merge queue will wait for required checks to be reported before it can proceed with merging."

### A2. `merge_group` event vs `pull_request`

"You **must** use the `merge_group` event to trigger your GitHub Actions workflow when a pull request is added to a merge queue." The reusable note that GitHub repeats in four places (merge queue doc, events reference, troubleshooting status checks, troubleshooting rules): "If your repository uses GitHub Actions to perform required checks or if you require workflows via organization rulesets on pull requests in your repository, you need to update the workflows to include the `merge_group` event as an additional trigger. Otherwise, status checks will not be triggered when you add a pull request to a merge queue. **The merge will fail as the required status check will not be reported.** The `merge_group` event is separate from the `pull_request` and `push` events."

Event semantics (Events that trigger workflows): activity type `checks_requested` only; `GITHUB_SHA` = "SHA of the merge group"; `GITHUB_REF` = "Ref of the merge group". The webhook doc: "When you receive this event, you should perform checks on the head SHA and report status back using check runs or commit statuses." The `destroyed` action carries `reason` ∈ {`merged`, `invalidated`, `dequeued`}: "invalidated by an earlier queue entry being dequeued" — this is the signal that a group was rebuilt.

**Path filters and merge_group.** The `merge_group` event does not carry `paths`/`paths-ignore` filters in the reference table, and GitHub's guidance is blunt: "You should not use path or branch filtering to skip workflow runs if the workflow is required to pass before merging." When a workflow is skipped by path filtering, branch filtering, or a `[skip ci]` commit message, "Associated checks stay in a 'Pending' state and block merging" (Troubleshooting required status checks, "Handling skipped but required checks"). The documented outcome is the PR (or queue entry) being blocked with "Waiting for status to be reported"; in the queue this then hits the status-check timeout and the entry is removed ("Timed out awaiting a successful CI result").

**Required workflows (org rulesets) and merge queue.** "Ruleset workflows support using the `pull_request`, `pull_request_target` and `merge_group` events... **Any filters you specify for the supported events are ignored** — for example, `branches`, `branches-ignore`, `paths`, `types`... The workflow is only triggered, and is always triggered, by the default activity types of the supported events" (default for `merge_group` is `checks_requested`). Additional documented constraints: ruleset workflows "do not run on events triggered by the `GITHUB_TOKEN`"; "Verify that your ruleset workflow does not use the `cancel-in-progress` concurrency setting"; "If you create a rule while a pull request is open, the required workflow will not run automatically"; "If a ruleset workflow runs in 'Evaluate' mode and passes, you can set the ruleset workflow to 'Active' mode and merge your pull request without triggering a new workflow run."

### A3. Base movement, failed groups, reconstruction, races

- **Failure cascade:** "When the GitHub API receives a failing status for `main/pr-1`, the merge queue automatically removes pull request #1 from the merge queue. The merge queue recreates the temporary branch with the prefix of `main/pr-2` to only contain changes from the target branch and pull request #2." Each downstream entry gets a **new head_sha** and a fresh `checks_requested` dispatch; the old group emits `destroyed` with `reason: invalidated`.
- **Jump the queue:** "jumping to the top of a merge queue will cause a full rebuild of all in-progress pull requests, as the reordering of the queue introduces a break in the commit graph." Audit log records `merge_queue.pull_request_queue_jump`.
- **Removal reasons** (documented): CI reporting failures for a merge group; timeout per configured setting; "User requesting a removal via the API or merge queue interface"; "Branch protection failure that could not automatically be resolved". Also "if there are failed required status checks or conflicts with the base branch, the pull request will be removed from the queue. The pull request timeline will display the reason."
- **Base movement:** by construction, each group is built on "the latest version of the `base_branch`" at group creation time. The docs do not describe what happens if the base branch is updated *outside* the queue (an admin direct push, or a bypass merge) while groups are in flight; the safe reading is that in-flight groups whose `base_sha` no longer equals the base tip are rebuilt, but this is **not documented** and should be treated as a gap (Part C).
- **Timing/race surfaces documented:** build concurrency throttles `checks_requested` dispatch ("When it receives a result for one of those pull requests, merge queue will dispatch the event for the 4th pull request"); status-check timeout treats missing conclusions as failure; the 2026-02-19 changelog "Changes to test merge commit generation for pull requests" changed *when* test-merge commits are generated for open PRs (announced as reducing delays and improving reliability — full text not fetched; consumers relying on `merge_commit_sha` freshness should re-verify).
- **Stacked PRs (public preview, 2026-07-30 changelog):** merge queue support "began rolling out progressively in July–August 2026". Not documented in the fetched reference docs; treat interactions as unknown.

### A4. Required checks: merge group vs PR head; can a merge occur on a check that passed on a different SHA?

- To *enter* the queue: "Once a pull request has passed all required branch protection checks, a user with write access to the repository can add the pull request to the queue" — these are checks on the PR (head SHA, or the PR's test-merge commit: "Test merge commit has a status → the test merge commit must pass; Test merge commit has no status → the head commit", Troubleshooting required status checks). The button "Merge when ready" can be clicked earlier; "GitHub adds the pull request to the queue when requirements are met."
- To *merge* from the queue: only the checks reported on the merge-group `head_sha` count. The PR's own checks are **not** re-run; the queue dispatches a new event for a new SHA.
- So yes — by design the commit that lands on base was tested under a *different SHA* from the PR head (the group commit), and under HEADGREEN it may even be a *different group commit* than the one for that PR. Additionally, outside a queue: "Pull requests that are up-to-date and pass required status checks can be merged locally and pushed to the protected branch. You can do this without running status checks on the merge commit itself." And "Required checks must pass on the latest commit SHA. Checks from earlier commits don't satisfy the requirement."
- Retention: "A required status check must have completed successfully in the chosen repository during the past seven days" to be selectable; checks data is retained 400 days then archived; "To merge a pull request with checks that are both required and archived, you must rerun the checks."

### A5. Bypass / jumping the queue

- Admin bypass at merge time: "if you are an administrator, you can: Directly merge the pull request by checking **Merge without waiting for requirements to be met (bypass branch protections)**, if allowed by branch protection settings" (Merging a PR with a merge queue). GraphQL exposes `PullRequest.viewerCanMergeAsAdmin`.
- Ruleset bypass actors: eligible are "Repository admins, organization owners, and enterprise owners; The maintain or write role, or custom repository roles based on the write role; Teams (excluding secret teams); Enterprise teams, enterprise apps, and enterprise roles (public preview, GHEC); Deploy keys (GHES); GitHub Apps; Dependabot; Copilot cloud agent (GHEC)". Individual users were added as bypass actors per the 2026-05-07 changelog ("Repository rulesets: User bypass and branch renaming"). Bypass modes: "Always allow" or "For pull requests only" — "The selected actor is now required to open a pull request to make changes... The actor can then choose to bypass any branch protections and merge that pull request." A third mode, **exempt** ("lets you exempt specific actors from all enforced rules, which unlike a standard bypass silently skips enforcement"), shipped 2025-09-10 ("GitHub ruleset exemptions and repository insights updates"); the full text was not fetchable, but the summary's word *silently* is the crux — see Part B.
- Classic branch protection: "By default, the restrictions of a branch protection rule do not apply to people with admin permissions to the repository or custom roles with the 'bypass branch protections' permission" unless "Do not allow bypassing the above settings" (`enforce_admins`) is enabled.
- Queue jump: any user adding a PR can pick "move your pull request to the top of the queue"; this is not a bypass of checks, just ordering (audit: `merge_queue.pull_request_queue_jump`).

### A6. APIs and webhooks available to a GitHub App

**GraphQL (schema 2026-09-19):**
- `Repository.mergeQueue(branch:)` → `MergeQueue { configuration: MergeQueueConfiguration, entries(...): MergeQueueEntryConnection, nextEntryEstimatedTimeToMerge, repository, url }`.
- `MergeQueueEntry { baseCommit: Commit, headCommit: Commit, enqueuedAt, enqueuer: Actor!, estimatedTimeToMerge, jump: Boolean!, position: Int!, pullRequest, solo: Boolean!, state: MergeQueueEntryState! }` with states `AWAITING_CHECKS, LOCKED, MERGEABLE, QUEUED, UNMERGEABLE`.
- `MergeQueueConfiguration { checkResponseTimeout, maximumEntriesToBuild, maximumEntriesToMerge, mergeMethod, mergingStrategy, minimumEntriesToMerge, minimumEntriesToMergeWaitTime }`.
- `PullRequest { mergeQueueEntry, isInMergeQueue, mergeQueue, isMergeQueueEnabled, mergeStateStatus (BEHIND/BLOCKED/CLEAN/DIRTY/HAS_HOOKS/UNKNOWN/UNSTABLE), potentialMergeCommit, headRefOid, baseRefOid, autoMergeRequest, reviewDecision, statusCheckRollup, mergedBy, mergeCommit, viewerCanMergeAsAdmin }`.

**Webhooks (OpenAPI x-webhooks, 2026-09-19):**
- `merge_group` `checks_requested` / `destroyed` (with `reason`). `supported-webhook-types: ["app"]` — **only GitHub Apps** can subscribe; repository/organization webhooks cannot. The docs' permission requirement for this event is the "Merge queues" repository permission (read) — `app-permissions.merge_queues`: "The level of permission to grant the access token to manage the merge queues for a repository."
- `pull_request` actions `enqueued` / `dequeued` (repo, org, app), `auto_merge_enabled` / `auto_merge_disabled`.
- `branch_protection_rule` created/edited/deleted; `branch_protection_configuration` enabled/disabled ("All branch protections were disabled for a repository"); `repository_ruleset` created/edited/deleted; `check_run`, `check_suite`, `workflow_run`, `workflow_job`, `pull_request_review` (incl. `dismissed`), `deployment_protection_rule` (`requested`, app-only).
- Not present in the OpenAPI x-webhooks: any `bypass_request_*` / `exemption_request_*` events (those exist for push rules/secret scanning in the docs generator but are not in the fetched OpenAPI). There is **no webhook for "a bypass was used to merge"**, no webhook for a rule-suite evaluation result, and no webhook carrying the merge-queue *group composition*.

**REST (permission mapping from `github/docs` server-to-server-permissions data, 2026-09-19):**
- `GET /repos/{o}/{r}/rulesets`, `GET .../rulesets/{id}`, `GET .../rules/branches/{branch}` → **Metadata (read)**, i.e. every app can read active rules. But "To prevent leaking sensitive information, the `bypass_actors` property is only returned if the user making the API request has write access to the ruleset."
- `GET .../rulesets/rule-suites` and `.../rule-suites/{id}` → **Administration (read)**; org-level `GET /orgs/{org}/rulesets/rule-suites` → **Organization Administration (write)** per the generated mapping.
- `GET .../rulesets/{id}/history` → **Administration (write)** (repo) / Org Administration (write).
- Classic protection: `GET .../branches/{b}/protection`, `/enforce_admins`, `/required_status_checks`, `/required_pull_request_reviews`, `/restrictions` → **Administration (read)**.
- Checks/statuses: `GET .../commits/{ref}/check-runs` (Checks read), `GET .../commits/{ref}/status|statuses` (Commit statuses read); Actions runs/jobs/attempts/logs (Actions read); environments and deployment protection rules (Actions read).
- PR reviews and dismissals: `GET .../pulls/{n}/reviews` (Pull requests read); `PUT .../reviews/{id}/dismissals` (write).

**What is not exposed:** the merge-queue "group" as a first-class object with its list of member PRs and the exact `head_sha` used for the final base update (you can reconstruct from `merge_group` webhooks + `MergeQueueEntry.headCommit`, but there is no historical query for destroyed groups); the audit log via API on non-Enterprise plans; who clicked "Merge without waiting"; the bypass-mode of a bypass actor except through the ruleset object (and only with write access).

### A7. Known limitations, edge cases, misconfigurations (documented)

- "A merge queue cannot be enabled with branch protection rules that use wildcard characters (`*`) in the branch name pattern."
- "Require merge queue" and "Require deployments to succeed" are **not available in organization-level rulesets**.
- Required-check naming: "Workflow: `<job name>`; Reusable workflow: `<job name> / <reusable job name>`... Required status checks do not take workflow, matrix, or event trigger types into account." And "make sure that job names are unique across all workflows. Using the same job name in multiple workflows can cause ambiguous status check results."
- Checks from workflows triggered by `workflow_dispatch`, `schedule`, etc. "do not appear in the pull request's checks section... Even if the checks pass for the head commit, they do not satisfy a required status check." Only `push`, `pull_request`, `pull_request_review`, `pull_request_target`, `deployment`, `deployment_status` (and `merge_group` for the queue) count. "This restriction applies only to checks created by workflow jobs, not to checks created by an external GitHub App."
- "Status checks are not indexed for rulesets defined above the repository level. You must manually enter the exact check name expected."
- "GitHub does not log rule insights until a pull request is merged or a merge is attempted." (Rule insights are merge-time, not evidence-time.)
- Indirect merges: "Pull requests merged indirectly are marked as `merged` even if branch protection rules on that pull request were not satisfied." Audit: `pull_request.indirect_merge`.
- Recent changelog (2025–2026, titles/dates from search results): "Improved pull request merge experience is now generally available" (2025-03-04); "Pull request merge experience — April 3 update" (2025-04-03); "Pull request 'Files changed' public preview and merge experience — November 6 updates" (2025-11-06: merge queue page now shows optional checks for queued PRs); "Changes to test merge commit generation for pull requests" (2026-02-19); "Quick access to merge status in pull requests" (public preview, 2026-03-05); "GitHub Actions concurrency groups now allow larger queues" (2026-05-07); "Stacked pull requests are now in public preview" (2026-07-30, merge-queue support rolling out); rulesets: "Push rule delegated bypass... GA and repository policy delegated bypass in preview" (2025-04-09); "GitHub ruleset exemptions and repository insights updates" (2025-09-10); "Delegated bypass controls for push protection now available at the enterprise level" (2025-09-16); "Configure Copilot coding agent as a bypass actor for rulesets" (2025-11-13); "Rule insights dashboard and unified filter bar" (2026-04-16); "Repository rulesets: User bypass and branch renaming" (2026-05-07); "Rule insights for organizations in public preview" (2026-08-12); "Rule insights dashboard generally available" (2026-08-25).

## PART B — Mechanisms that change the meaning of "green"

Legend for observability: **Meta** = Metadata:read (any app); **Admin:r** = Administration:read; **Org-audit** = organization audit log (UI, 180 days; API only on GHEC); **Ent** = Enterprise only.

### B1. Ruleset bypass actors, bypass modes, delegated bypass, rule insights
- **Configuration**: rulesets readable by any app (Meta) but `bypass_actors` are hidden unless the token has write access to the ruleset. So a read-only app **cannot see who is allowed to bypass** a ruleset it did not create, nor their mode (always / pull-request-only / exempt).
- **Usage**: Rule insights (rule suites) record every evaluated ref update with `result: pass|fail|bypass`, `actor_name`, `before_sha`, `after_sha`, `ref`, `pushed_at`, and per-rule `rule_evaluations[{rule_source, enforcement (active|evaluate|deleted ruleset), result, rule_type, details}]`. Needs **Admin:r** at repo level; the `time_period` filter caps at `month` (hour/day/week/month), which strongly implies a ~30-day query window. Insights are logged only "until a pull request is merged or a merge is attempted". The rule insights dashboard (repo + org, GA 2026-08-25, Team/GHEC plans) surfaces "Successes, failures, and bypasses over time" and "Top bypassers" in the UI; org-level CSV export exists.
- **Exempt bypass (2025-09-10)**: described as *silently skipping enforcement* — by that description it would not appear as a `bypass` result in rule insights. Treat as an observability hole until verified against the full changelog text.
- **Delegated bypass** (request/approve flow) is documented **only for push rulesets** (restricted file paths/size/extensions) and secret-scanning push protection; there is no delegated-bypass request flow for branch rules like required checks or reviews. Requests are visible on the repository's "Bypass Requests" settings page; statuses Cancelled/Completed/Denied/Expired/Open; 7-day validity.
- **Audit log**: `repository_ruleset.create|update|destroy` with fields including `ruleset_bypass_actors_added/deleted/updated`, `ruleset_rules_added/deleted/updated`, `ruleset_enforcement`, `ruleset_old_enforcement`. Ruleset history (UI/REST, Admin:write) "lists events... within the last 180 days" and lets you "download a JSON file containing the ruleset's configuration at a specific iteration. **The bypass list of a ruleset is excluded from the exported JSON file.**"
- **Webhook**: `repository_ruleset` created/edited/deleted (repo/org/app).

### B2. Classic branch protection "Include administrators" / `enforce_admins`
- Readable via `GET .../protection/enforce_admins` (**Admin:r**). Audit: `protected_branch.update_admin_enforced` (`admin_enforced` field), and when an admin overrides, `protected_branch.policy_override` ("A branch protection requirement was overridden by a repository administrator") with fields `before`, `after`, `branch`, `overridden_codes`, `reasons`, `rule_suite_id`, `compliant_pull_request_ids`. This is the richest "who bypassed what" record GitHub has — and it is **audit-log only** (org owners; API on GHEC).
- Webhook: `branch_protection_rule` edited.

### B3. Direct pushes, force pushes, deletions
- Rulesets: Restrict updates / Block force pushes / Restrict deletions (only bypass actors can do them). Classic: default blocks force push and deletion; "People and apps with admin permissions to a repository are always able to push to a protected branch or create a matching branch" (unless enforce_admins). Force push "can also be used to delete branches or point a branch to commits that were not approved in a pull request."
- Observability: `push` webhook (`forced: true` flag on the payload), rule suites (`before_sha`/`after_sha` per push, result bypass), audit `protected_branch.rejected_ref_update` for blocked attempts. "Require a pull request before merging" ensures "all changes... be associated with a pull request", but indirect merges still mark PRs merged even when rules were not satisfied.

### B4. Required status checks semantics
- **Strict vs loose**: "Require branches to be up to date before merging" (strict) forces the head to include the base tip; loose allows merging a PR tested on a stale base ("Status checks may fail after you merge your branch if there are incompatible changes"). The queue "provides the same benefits as... up to date... but does not require a pull request author to update". Readable via protection API (Admin:r) or `rules/branches/{branch}` (Meta; `strict_required_status_checks_policy`).
- **Checks named but not reported**: "expected" status ("The check run is waiting for a status to be reported"); PR shows "Waiting for status to be reported" and is blocked; in the queue it times out.
- **Renamed/disappeared checks**: if a required name is never reported again the branch is simply blocked; no alert. Rulesets above repo level do not index names.
- **Skipped/neutral count as pass**: "Required status checks must have a `successful`, `skipped`, or `neutral` status before collaborators can make changes to a protected branch." "A job that is skipped will report its status as 'Success'. It will not prevent a pull request from merging, even if it is a required check." "A job depends on a failed job → The dependent job is skipped and may not block merging." Whole-workflow skips (path filter, `[skip ci]`) stay Pending and block; **job-level `if:` skips pass**. `continue-on-error: true` steps/jobs also yield success conclusions.
- **Expected source app**: a required check can be pinned to a specific GitHub App ("If the status is set by any other person or integration, merging won't be allowed"). Otherwise "Any person or integration with write permissions to a repository can set the state of any status check in the repository" — commit statuses are forgeable by any write-capable actor; the merge box lists the author of each status.
- **Concurrency cancellation**: cancelled runs yield `cancelled` conclusions (block); but ruleset workflows must not use `cancel-in-progress` (documented misconfiguration).
- Observability: check runs (Checks:r) include `app`, `head_sha`, `conclusion`, `check_suite`, `details_url`; workflow runs (Actions:r) include `event` (`pull_request` vs `merge_group`), `head_sha`, `path`, `run_attempt`, `triggering_actor`. Reading the *definition* of a workflow requires Contents:r; `workflows` permission is only for writing.

### B5. Required workflows, workflow-file changes, `pull_request_target`, post-evidence modifications
- Org/enterprise "Require workflows to pass before merging" pins a workflow file in a *source* repository (so a PR in the target repo cannot edit it), but per-repo required checks are produced by workflow files in the PR itself. GitHub's own mitigation is CODEOWNERS on `.github/workflows` ("any proposed changes to these files will first require approval") plus ownership of the CODEOWNERS file itself.
- `pull_request_target` "runs in the context of the default branch of the base repository... prevents execution of unsafe code from the head"; the warning: "Running untrusted code on the `pull_request_target` trigger may lead to security vulnerabilities" — and such checks *do* satisfy required checks (it is in the eligible event list).
- Ruleset workflows ignore filters, don't run on `GITHUB_TOKEN`-triggered events, don't auto-run for PRs open at rule creation, and a run passed under Evaluate carries over to Active "without triggering a new workflow run".
- Audit (org): `workflows.created_workflow_run`, `completed_workflow_run`, `prepared_workflow_job` (API/streaming/export only), `rerun_workflow_run`, `disable_workflow`, `actions_policy_violation`, `bypass_protection_rules`.

### B6. Approvals
- **Dismiss stale**: "GitHub records the state of the diff at the point when a pull request is approved... If the diff changes from this state (for example, because a contributor pushes new changes... or clicks **Update branch**, or because a related pull request is merged into the target branch), the approving review is dismissed as stale." With dismiss-stale or last-push-approval, "approving reviews will be dismissed as stale if the merge base introduces new changes after the review was submitted" and "manually creating the merge commit... and pushing it directly to a protected branch will fail, unless the contents of the merge exactly match".
- **Require approval of most recent reviewable push**: "'stale' reviews are not dismissed, and the pull request remains approved as long as someone other than the person who made the most recent changes approves it... If you are concerned about pull requests being 'hijacked' (where unapproved content is added to approved pull requests), it is safer to dismiss stale reviews." Without either option, an approval on commit A remains valid after commit B is pushed — a documented, legitimate weakening.
- **CODEOWNERS**: "an approval from *any* of the owners is sufficient"; "Required reviewers" (team + file patterns, up to 15 teams) is the stricter ruleset option.
- **Dismissal**: "anyone with write permissions for the repository can dismiss the blocking review" unless dismissal is restricted; dismissal requires a comment; audit `pull_request_review.dismiss`; webhook `pull_request_review.dismissed`. Overlapping-commit rule: cannot merge if another open PR with the same head commit has pending/rejected reviews.
- **Apps approving**: apps with Pull requests:write can submit reviews; whether they count toward required approvals depends on them having write access (docs: "approved by the required number of reviewers with write permissions"). Copilot-authored PRs now require an additional approval by default (public preview).
- Observability: reviews + `commit_id` per review (Pull requests:r); `reviewDecision`, `latestOpinionatedReviews` (GraphQL); `pull_request_review` webhooks. Whether an approval covers the merged SHA must be computed by the observer.

### B7. Auto-merge, Update branch/Rebase, merge method and which SHA gets tested
- Auto-merge "merges a pull request automatically after all required reviews and status checks pass"; "disabled if someone without write permissions pushes new changes to the head branch or switches the base branch." `gh pr merge` on a queue-required branch "automatically adds the pull request to the queue if required checks have passed. If required checks have not passed, this command enables auto-merge." Webhook `pull_request.auto_merge_enabled/disabled`; GraphQL `autoMergeRequest`.
- "Update branch" (merge base into head) or "Rebase" create new head SHAs (rebase "will always update the committer information and create new commit SHAs"), triggering new PR checks; both can dismiss stale approvals.
- Test-merge commit: the PR's `merge_commit_sha` is a throwaway test commit; checks run "for the merge commit" when present. Squash/rebase merges produce SHAs that were never tested as such; a merge-commit merge outside a queue produces a commit whose content equals the test-merge commit only if the base did not move (loose mode allows it to move).

### B8. Deployment environment protection rules and bypass
- "By default, administrators can bypass the protection rules and force deployments"; environments can "disallow bypassing the protection rules for all deployments"; bypass is only possible while a job is Pending; the UI requires a comment. Audit `workflows.bypass_protection_rules` (fields `workflow_run_id`, `run_number`). "Require deployments to succeed before merging" rule ties a branch to successful deployments. Deleting an environment "will delete all secrets and protection rules... jobs currently waiting... will automatically fail." Audit `environment.add/update/remove_protection_rule`, `environment.delete`.
- Observability: environments & rules (Actions:r), `deployment_protection_rule` webhook (app-only), pending deployments (Actions:r).

### B9. GitHub App permission limits (summary)
| Need | Permission | Notes |
|---|---|---|
| Active rules for a branch, rulesets | Metadata:read | `bypass_actors` hidden without write |
| Classic protection incl. enforce_admins, strict, contexts, restrictions | Administration:read | |

| Enterprise rulesets, enterprise teams/apps as bypass actors, delegated bypass at enterprise level | Enterprise | |

### B10. "Who bypassed what" availability to apps
- Available: rule suites (`result: bypass`, `actor_name`, per-rule results) — Admin:r, merge-time only, short window; `merge_queue.*` and `protected_branch.policy_override` — audit log only.
- Not available: a per-PR/merge-time flag saying "this merge used bypass" via REST/GraphQL PR objects or webhooks; the bypass actor's *mode*; exempt-actor usage (if truly silent); who approved a delegated bypass (push rules only, UI page).

### B11. Repository settings changing between evidence and merge
- Webhooks `repository_ruleset.edited`, `branch_protection_rule.edited`, `branch_protection_configuration.disabled` give near-real-time notice (repo/org/app). Rule suites and ruleset history preserve *what applied at evaluation time* (`enforcement: "deleted ruleset"` is even an enum value), but ruleset history is Admin:write and 180 days; rule suites ~30 days. There is no API that answers "which exact ruleset version applied to merge X" beyond correlating `rule_suite_id` (also present on `policy_override` audit rows).

## PART C — The "native GitHub challenge"

### The strongest honest case for "you need nothing else"

A customer that (1) requires a merge queue on `main` with **ALLGREEN**, a status-check timeout, and (2) has CI on `on: [pull_request, merge_group]` with no path filters and no job-level `if:` on required jobs, (3) uses an **organization ruleset with no bypass actors** (so not even org owners or apps can bypass; rulesets, unlike classic protection, have no implicit admin exemption), Block force pushes, Restrict deletions, Require a pull request, dismiss stale approvals **and** last-push approval, required conversation resolution, required signed commits, (4) pins required checks to the expected GitHub App (Actions) so commit statuses from write-capable actors cannot impersonate them, (5) uses an org-level **required workflow** from a locked-down source repo so the gating workflow definition cannot be edited from the PR, (6) has CODEOWNERS covering `.github/` including CODEOWNERS itself, (7) sets Actions policies (allowed actions, default `GITHUB_TOKEN` read-only, fork-PR approval), and (8) is on GHEC with audit-log streaming — gets, from GitHub alone:

- Every commit on `main` arrived via a queue merge of a group commit whose required checks (from the pinned app, on that exact `head_sha`, with cumulative base state) reported success within the timeout; nothing else can update the ref because there are no bypass actors and force pushes/deletions are blocked. Rule suites record every ref update with pass/fail/bypass. Audit streaming retains `pull_request.merge`, `merge_queue.*`, `repository_ruleset.update`, and workflow run events indefinitely in the customer's SIEM.
- Approvals are bound to the diff (stale dismissal) and to the last push (last-push approval), so no unreviewed content can ride an old approval.
- The workflow that gates merging is defined outside the PR (required workflow) and cannot be path-filtered away.

This is a strong position. For most of what a receipt product would check on the *happy path*, GitHub's enforcement is real, server-side, and not bypassable by the PR author. If the pitch is "GitHub doesn't enforce its rules", it is false.

### The residual gaps (concrete, with severity)

1. **Evidence is not bound to the merged candidate across queue reconstruction — medium.** The commit that lands is a group `head_sha` created by the queue; that SHA changes on every invalidation (`destroyed: invalidated`) or queue jump. GitHub keeps no queryable history of destroyed groups, their member PRs, or which group commit's checks satisfied the final merge. `MergeQueueEntry.headCommit` exists only while the entry is live. After the merge, the PR object has `mergeCommit` but nothing linking it to the `merge_group` run that tested it; you reconstruct it by matching `workflow_run.head_sha` (event `merge_group`) to the base branch's new tip. With `mergeMethod: SQUASH/REBASE`, the merged SHA differs from every tested SHA. Under **HEADGREEN**, a PR whose own group commit failed can land — GitHub's UI shows the merge as successful. A receipt that says "these exact check runs passed on this exact landed commit" is not something GitHub emits.

2. **Skipped/neutral count as pass — small but real.** Documented: a job skipped by `if:` "will report its status as 'Success'. It will not prevent a pull request from merging, even if it is a required check"; `neutral` conclusions also satisfy required checks; a job whose `needs` failed is skipped "and may not block merging". So a required check name can be satisfied without the test having run. GitHub records the `skipped`/`neutral` conclusion (visible via Checks:r), but it does not distinguish it from `success` for gating and does not flag it. A receipt policy that treats `skipped`/`neutral` as NOT_PROVEN is a genuine addition.

3. **Workflow definition drift between evidence and merge — medium unless required workflows are used.** For repository-defined workflows, the gating YAML lives in the PR head; GitHub's only mitigations are CODEOWNERS and Actions policies. A PR can legitimately modify the workflow (loosening tests) and the `pull_request`/`merge_group` runs will use the modified definition; nothing records "the check named `build` was produced by workflow file at blob X". Required workflows close this at the org level, but they are unavailable to Free/Pro and cannot carry `paths` filters; many teams do not use them. The observer must fetch the workflow file at the tested SHA (Contents:r) and include its blob SHA in the receipt.

4. **Bypass usage is not visible at merge time to a read-only app — medium.** `bypass_actors` are hidden from read-only tokens; rule suites need Administration:read and are only written at merge/push time with a ~30-day window; `protected_branch.policy_override` and `merge_queue.pull_request_dequeued` are audit-only (180 days UI, API only on GHEC). "Merge without waiting for requirements" is an admin path whose footprint is an audit row, not a PR field. The **exempt** bypass type (2025-09-10) is described as silently skipping enforcement, which would leave no rule-insight trace. Ruleset JSON exports/history **exclude the bypass list**. Net: GitHub knows who bypassed, but the knowledge is scattered across surfaces with different permissions, retention, and plan gating, and there is no single "this merge was clean vs. bypassed" bit on the PR.

5. **Historical reconstruction of the rules that applied at merge time — medium.** Rulesets can be edited or disabled and re-enabled between evidence and merge; `rule_suite_id` links a specific evaluation to the ruleset(s) in force, but ruleset history is Administration:**write** and 180 days, rule suites ~30 days, and classic branch-protection changes are only in the audit log. Evaluate-mode passes carry over to Active without a re-run. An observer that snapshots `rules/branches/{branch}` + `rulesets/{id}` at enqueue time and again at merge time, and diffs them, provides something GitHub does not.

6. **Loose (non-strict) checks and out-of-queue merges — small if queue is required; large otherwise.** Without a queue and with strict off, a PR tested on a stale base can merge; docs explicitly allow merging locally "without running status checks on the merge commit itself". Indirect merges mark PRs merged "even if branch protection rules... were not satisfied."

7. **Commit statuses are trivially forgeable by any write-capable actor unless pinned to an app — small if pinned.** "Any person or integration with write permissions... can set the state of any status check." Pinning to an app is per-check and easy to forget; the merge box shows the author but nothing alerts.

8. **Approval freshness is the observer's job — small.** GitHub stores the review's `commit_id`; whether that review covers the merged SHA (or the group commit that includes other PRs) is not asserted anywhere. With last-push-approval off and stale-dismissal off, an approval of commit A legitimately authorizes commit B.

9. **Base movement outside the queue is undocumented — unknown.** The docs do not state what the queue does if the base tip changes by a bypass push while groups are in flight. Merge-Proof should verify `merge_group.base_sha == base tip at merge time` rather than assume.

10. **Plan/permission gating of GitHub's own evidence — structural.** Rule insights need Admin:read; org insights need Org Admin; audit API and streaming need GHEC; enterprise-level bypass actors and rulesets need Enterprise. A vendor that only ever asks for Metadata/Checks/Statuses/Actions/Pull requests/Merge queues (read) is *less* privileged than GitHub's own insights and must say so honestly: it can prove what checks ran on which SHA and what rules were active, but cannot prove "no bypass occurred" without Administration:read (rule suites) — and even then only for ~30 days, and not for exempt actors.

Where a gap is small: (2), (7), (8) are each closable by a customer who configures carefully; (6) disappears with a required queue. Where it is not: (1), (3), (4), (5) have no single GitHub surface today; the value of an independent receipt is precisely binding *candidate SHA + check runs + workflow blob + applied rules + bypass evidence* into one record with a freshness verdict, using data GitHub exposes but never joins.

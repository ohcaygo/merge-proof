# Merge-Proof competitor teardown (source-level)

Date: 2026-09-19. Method: every repository below was cloned with `git clone --depth 50` into `scratchpad/l2/competitors/` and read statically. No competitor code was executed against any real repository. Metadata (stars, created/pushed dates, license) comes from the GitHub repository objects; commit counts marked "≥50" are truncated by the shallow clone. File:line citations refer to the clone at the commit listed in each header.

Merge-Proof reference model (from the brief): hosted GitHub App; deterministic receipt `VERIFIED / NOT_PROVEN / FAIL` × freshness `CURRENT / STALE / UNAVAILABLE`; subject is the applicable CI target (head if it contains base, else GitHub's test-merge ref with matching parents, else a live merge-group entry); two matching complete observations; distinguishes check conclusions from workflow run/job/step execution on that SHA (skipped step = no execution proof); current-head approval by a non-author with observed write permission; rulesets ∩ classic protection; remote ref durability; actor classification; immutable merge ledger row; optional Check; gaps / notChecked / limitations; no model; own check excluded from its own requirements.

## 1. Aryamanz29/mergeproof (mandatory, deepest)

**Identity.** https://github.com/Aryamanz29/mergeproof · MIT · Python 3.11+ (pydantic, httpx, PyYAML) · 142 commits · first commit 2026-09-12, last 2026-09-16 (HEAD `f65500a`) · 1 star, 0 forks · tags `v0.6.0, v1, v1.0.0, v1.0.1, v1.0.2` · PyPI `mergeproof` 1.0.2 (releases 0.2.0…1.0.2) · **Action/CLI only; not a hosted App** (`action.yml` is a composite action that `pip install`s the package and runs `mergeproof check --github`, `action.yml:60-93`). The repo also carries a `Dockerfile`, `CLAUDE.md` and `AGENTS.md`; the whole history is four days old, so this is a fast, agent-assisted build rather than a mature product.

**What it is.** A *declared-policy evidence gate*. One `mergeproof.yaml` in the repository lists rules of the form `when: {paths, labels, title, base_branches, authors}` → `require: [{check, with}]` (`src/mergeproof/policy.py:23-71`). The engine matches rules against a `Context` and runs each check (`src/mergeproof/engine.py:36-91`). Verdict = worst blocking outcome; exit codes `0 pass/warn, 1 fail, 2 pending, 3 usage` (`src/mergeproof/report.py:26-27,100-112`).

**Data it reads (GitHub mode).** `providers/github.py:84-159` builds the whole context from REST:
- `GET /repos/{r}/pulls/{n}` (title, body, author, labels, base ref/sha, **head sha**, merged, merge_commit_sha, merged_by);
- `GET /pulls/{n}/files`; `GET /issues/{n}/comments`; `GET /pulls/{n}/reviews` (keeps `state` and `commit_id`, `github.py:99-110`); `GET /pulls/{n}/comments`;
- `GET /git/trees/{head_sha}?recursive=1`; `GET /commits/{head_sha}/check-runs` (`name, status, conclusion, started_at` only, `github.py:128-137`).
No GraphQL, no `/rules/branches`, no `/branches/.../protection`, no workflow-run/job/step endpoints, no collaborator permission lookup **in the gate**. (`doctor.py:336-356` does read `GET /repos/{r}/rules/branches/{b}` and `GET /branches/{b}/protection/required_status_checks`, but only to warn the installer that the `mergeproof` status is not required; it is not part of the PR decision.)

**Subject identity.** Head SHA of the PR, full stop (`github.py:121`). No merge-ref selection, no test-merge parent matching, no `merge_group` event handling (the doctor's event list is `pull_request`, `issue_comment`, `check_suite`, `doctor.py:231-282`). The receipt records `merge_commit_sha` after the fact, but nothing is evaluated on it.

**Freshness/staleness.** There is no observation model; one API snapshot is evaluated per run. Staleness exists only as *commit binding* of human evidence: an approving review must have `commit_id == head_sha` (`checks/human_verified.py:123`), and a `/verified` comment must contain the 7-char head prefix (`human_verified.py:114,125`). Agent verdict blocks are likewise bound to the 7-char head (`checks/agent_verdict.py:219-224`). Nothing checks that the base has moved, nor that the ref still points at the observed SHA at decision time.

**Check semantics (`checks/ci_job.py`).** Newest run per name by `started_at` (`ci_job.py:19-25`). `failed` = completed with conclusion not in `success/skipped/neutral`; `succeeded` = conclusion `success` only (`ci_job.py:57-59`). Consequence: a *skipped* or *neutral* run is neither failure nor success, so with `min_matches: 1` it produces `fail("0 successful runs, need 1")` (`ci_job.py:68-69`) — the right answer, but the message says "0 successful runs" rather than naming the skip. Cancelled/timed_out count as failures. It reads **check-run conclusions only**; it never opens the workflow run, its jobs, or steps, so a job whose steps were all `if: false`-skipped but reported `success` is a pass. A missing run is `pending` by default (`missing: fail` optional, `ci_job.py:39,56`). Nothing binds a check-run name to an app or workflow: any app or workflow that creates a check-run named `unit` satisfies `ci.job_passed`.

**Approvals (`checks/human_verified.py`).** Binds approval to `commit_id == head_sha` (line 123) — genuinely the head-bound approval Merge-Proof also requires. Excludes the author (`exclude_author`, line 143). Bots = login ends with `[bot]` (`context.py:122-123`). **No reviewer-permission check**: unless the policy author enumerates `allowed_users`, any GitHub account that can post an approving review (anyone, on a public repo) satisfies the rule. No dismissal handling beyond GitHub's own review state; no `author_association`.

**Rulesets / protection / bypass / queue.** Not read in the gate; no bypass detection; no merge-queue support. The published signal is a **commit status** with context `mergeproof` (`github.py:192-206`), which the docs tell you to require in a ruleset (`docs/guides/github.md:35-50`). A commit status is not bound to an app identity: any workflow or token with `statuses:write` can post `mergeproof=success`.

**Publishing.** Sticky issue comment with marker (`github.py:162-175`), commit status (`195-206`), file-level review comments synced create/update/delete (`217-276`), step summary, `GITHUB_OUTPUT verdict`, JUnit/rdjson renderings (`action.yml:85-87`), and a **receipt**: on merge, `receipts/<merge_sha>.json` committed via the git-data API to an orphan branch `mergeproof-receipts` (`receipt.py:200-255`). The receipt is a plain JSON commit, not signed and not immutable (a force-push or branch delete removes it; the docs say to protect the branch with a ruleset if you want tamper evidence, `docs/guides/receipts.md:55`).

**Machine contract.** JSON report (`report.to_json`), JUnit, rdjson, `mergeproof context` JSON dump for replay, `mergeproof replay` against merged PRs (`replay.py`), `mergeproof schema` (JSON Schema for the policy), `mergeproof agent-prompt` and `mergeproof explain` for agents. There is no MCP server in the package; `examples/mcp-server/` is an example *policy for a repo that ships an MCP server*, not an MCP interface. Exit codes are the CI contract.

**Trust model.** Policy file is in the repository; the sample workflow checks out `github.event.repository.default_branch` so the PR cannot edit its own rules (`README.md:94`, `docs/guides/github.md:11`). However the workflow itself runs on `pull_request`, whose workflow file comes from the PR's merge ref, so a same-repo PR can rewrite `.github/workflows/mergeproof.yml` (change the checkout ref, set `pending-ok`, or just post the `mergeproof` status itself with the `statuses:write` token the workflow is granted). Evidence links in the PR body (`evidence.artifacts`, `evidence.links`) are **self-reported by the PR author**; the only verification is that a verifier resolves the URL (`http` = answers 2xx, `verifiers/base.py:3`, or a Langfuse/Braintrust plugin looks the id up). `shell` runs commands from the policy file in the base checkout with `MERGEPROOF_FILES/HEAD_SHA` env (`checks/shell.py:33-56`). `agent.verdict` lets an LLM reviewer's fenced block count as a requirement, restricted to `authors` logins (`agent_verdict.py:216`). `tests.changed` is a *diff-shape* check (a mapped test file was modified), not an execution check (`checks/tests_changed.py:46-60`). Unavailable data: GitHub HTTP errors `die()` with exit 3 (`cli.py:135-136`); a check that throws becomes `ERROR` which is treated as a block (`engine.py:88-89`, `report.py:102`); offline mode returns `pending` for GitHub-only checks. So it is fail-closed at the process level, but the *status* it posts is whatever the last successful run posted — a crashed run leaves a previous `success` status standing on the same SHA.

**Tests.** 145 `def test_` functions across `tests/unit` (36 in `test_checks.py`, 21 CLI, 15 providers, 15 render, 7 doctor …) and `tests/integration` (8: examples, pipeline, plugins), plus scenario JSON fixtures per example policy (`examples/*/scenarios/*.json`). Coverage is good for check semantics and rendering; there is no test of the GitHub write paths against a recorded API, and none for concurrency/late-arriving events.

**Versus Merge-Proof.**
- *They do better today:* a real, expressive policy language (`when`/`require` with path captures `{name}`), 11 check types, pluggable evidence verifiers (Langfuse/Braintrust), `replay` of a candidate policy against the last N merged PRs, `doctor` that validates the workflow/permissions/branch rules, `explain`/`template`/`agent-prompt` UX for agents, file-level review comments, JUnit/rdjson outputs, PyPI distribution, and documentation depth.
- *Merge-Proof does that they do not:* merge-candidate selection (test-merge ref, merge-group), two-observation confirmation, run/job/step execution proof vs conclusion, reviewer write-permission check, rulesets ∩ classic protection with bypass awareness, remote-ref durability, actor classification, app-identity-bound Check, immutable ledger, explicit `notChecked/limitations`, self-exclusion of its own check.
- *They could copy in days:* head-contains-base check (one `compare` call), reviewer permission lookup (`/collaborators/{u}/permission`), a `merge_group` event branch reading `merge_group.head_sha`, publishing a Check run under an app identity instead of a status, reading rulesets to warn about bypass actors.
- *Merge-Proof could copy in days:* the `when/require` policy shape or at least path-scoped requirements; `replay` against merged PRs to show what a stricter policy would have blocked; the `doctor` installer audit; head-bound `/verified <sha7>` comments as a lightweight human attestation; the sticky comment + review-comment sync pattern.
- *Significant engineering for them:* hosted App with webhook idempotency, merge-candidate resolution, execution-level proof, and a durable ledger — none of the current architecture (single-shot CLI in Actions) supports it.
- *Problem solved:* declared-policy/evidence requirements, with self-reported artifact links and diff-shape checks. Not exact-candidate integrity.

## 3. Agent Vigil — sulmusic2-star/agent-vigil

**Identity.** https://github.com/sulmusic2-star/agent-vigil · MIT · TypeScript (Node 20) · 299 commits · created 2026-08-15, first clone-visible commit 2026-08-30, pushed 2026-09-17 · 0 stars, 0 forks, 43 open issues · tags through `v0.25.0` · npm `@sulmusic/agent-vigil` 0.24.4 · **both**: a GitHub Action (`action.yml`), a CLI (`vigil`), and a Cloudflare-Worker GitHub App (`hosted/public-app/src/index.mjs`, 1048 lines) plus a merge-queue dispatcher Worker (`hosted/merge-queue-dispatcher/src/index.mjs`, 339 lines). 56.9k lines under `src/`+`test/`+`hosted/`; 858 `test()`/`it()` cases in `test/`, 156 in `test-hosted/`. Author "Tim Sullivan". The README is careful to say the App is "not a live public service" and that staging exercised PASS/FAIL/stale-head/merge-queue blocking only first-party.

**What it genuinely implements.** The core question is *"did this exact change produce the evidence the base-branch policy requires?"*, answered by **running the repository's tests against the exact candidate** in a candidate-only Docker boundary and reconciling agent claims (transcript test counts, changed-file claims) with observation. Checks listed in `README.md` "What it checks": exact base/head identity; base-owned policy and workflow bytes; fresh tests; claimed vs observed test counts; skipped/focused/weakened/patched/self-fulfilling tests (`src/detectors/reality.ts` 1604 lines, `src/detectors/agentic.ts`); a changed regression test that fails on base and passes on head; changed-path/line limits; protected policy/workflow/verifier paths. Verdicts: `PASS / FAIL / NOT CHECKED` — NOT CHECKED is explicitly "no merge decision; required evidence did not run or could not be bound safely to the current commit".

**Data it reads.** Hosted App: webhooks `pull_request`, `merge_group`, `check_run`, `deployment_protection_rule` (`index.mjs:1006`); `POST /repos/{r}/check-runs` with `head_sha`, `external_id` and `output.title: "NOT CHECKED"` while queued (`index.mjs:773-777`); `GET /commits/{sha}/check-runs?check_name=Agent Vigil&app_id=` to recover a lost create (`541-550`); `GET /collaborators/{login}/permission` requiring `admin|write` **for re-run requesters** (`562-565`); `GET /pulls/{n}` and `GET /git/ref/...` to validate a re-run still targets the same head / queued refs (`573-590`); installation tokens scoped per call (`checks:write, contents:read, pull_requests:read`). Public read-only receipt (`src/public-pr-receipt.ts:333-345,697-700`): `pulls/{n}`, `pulls/{n}/reviews`, `commits/{head}/check-runs`, `commits/{head}/statuses`. Outcome evidence (`src/github-evidence.ts`): actions run + jobs, counting `failedJobs` with conclusions `failure|cancelled|timed_out|action_required|startup_failure|stale` (`github-evidence.ts:214`).

**Subject identity.** PR head SHA for the check (`head_sha: target.headSha`), and for merge queues the event's `merge_group.base_sha/head_sha` (`hosted/public-app/src/index.mjs:196-199`; `src/merge-group.ts:74-78` refuses if the checked-out base/head differ from the event, and requires `policy-ref == event base`, line 84). It does not use GitHub's test-merge ref for ordinary PRs; it checks out the exact head and runs tests there.

**Freshness.** Commit binding: workspace tree must equal head SHA (`docs/THREAT_MODEL.md` "Execution boundary"; `WORKTREE` is always INCONCLUSIVE). Hosted: a check unfinished after one hour is completed as `failure/NOT CHECKED` (`index.mjs:806-815`). Public receipt: `CURRENT / HOLD / EXPIRED / REVOKED` continuity with a `maxAgeHours` window, `freshnessReferenceAt` = earliest of merge/approval/check timestamps, and `REVOKED` when an approved PR is closed unmerged (`public-pr-receipt.ts:493-540`). No "two observations" rule; idempotency is per webhook delivery ID in a Durable Object (`index.mjs:668-684`).

**Check semantics.** `SUCCESSFUL_CHECKS = {success}`, `NON_PROVING_CHECKS = {neutral, skipped}` counted as `unknown` with reason code `checks-neutral-or-skipped`, `FAILED_CHECKS = {failure, timed_out, cancelled, action_required, startup_failure, stale, error}` (`public-pr-receipt.ts:141-143,433-441`); latest run per `(app slug, name)` (`421-429`); statuses merged by context. This is conclusion-level, but it *does* key by app slug, which is closer to Merge-Proof than mergeproof's name-only matching. Step-level execution proof is not read from GitHub; Agent Vigil's answer to "did tests actually run" is to run them itself in its own boundary.

**Approvals.** Public receipt counts latest review per login in `approved/changes_requested/dismissed` states (`386-396`); no author exclusion, no permission check, no commit binding — and the receipt says so: `allowsProtectedAction: false`, `sufficiencyAssessed: false`, `PUBLIC_CLAIM_STATEMENT` (`138`). Maintainer mode reads `event.pull_request.user.login` for declaration attribution (`src/maintainer.ts:30`). Human declarations in PR bodies are verified for "attribution and syntax only" (`THREAT_MODEL.md` out-of-scope list).

**Rulesets / bypass / queue.** Does not read rulesets. Its documented position is that a required *status name* is not a trust root and that only an App-owned check or an org required-workflow ruleset binds the name to the intended verifier (`docs/MERGE_QUEUES.md` "Why the generated workflow is pull-request only"). Merge-queue path: a dispatcher Worker validates HMAC, allowlists repo/branch, records delivery ID, dispatches a trusted `main` workflow in the control repo which re-checks the queue ref and posts `Agent Vigil governed evidence` for the composed head (`MERGE_QUEUES.md` "Agent Vigil's external queue path"). `vigil doctor` fails a repository-owned `merge_group` workflow (`src/setup.ts:1165-1166`).

**Publishing / machine contract.** App-owned Check run named `Agent Vigil` with `PASS/FAIL/NOT CHECKED`; deployment-protection decisions; JSON receipts with JSON Schemas under `docs/*.schema.json` (receipt, authority plan, continuity, control certificate v1/v2, public PR receipt); optional Ed25519 signature and Sigstore attestation (`action.yml` `attest`); SARIF; CLI `vigil check <PR URL>`. Exit codes per mode. Extensive disclaimers (THREAT_MODEL, COMPETITOR_COMPARISON, COMMERCIAL_GATES).

**Trust model.** Policy is loaded from `policy-ref` = the PR **base** SHA through `pull_request_target` in the generated workflow (`THREAT_MODEL.md` "Policy integrity"); candidate code runs with no token, no network in tests (`isolate-candidate`); receipt hash is a content id, not a signature unless keys are pinned. The PR cannot change the policy that evaluates it in the hosted/`pull_request_target` lanes; it *can* in a naive repo-owned `pull_request` lane, which doctor rejects. Evidence is partly self-reported (agent transcripts, PR-body declarations) but reconciled against observed execution; that reconciliation is the product. Unavailable data fails closed to `NOT CHECKED` (a failure conclusion), never to pass.

**Tests.** 858 + 156 cases; includes adversarial fixtures per corrected false result, hosted Durable-Object flow tests (`test-hosted/public-app.test.ts`, `merge-queue-dispatcher.test.ts`), release-assembly and package-surface gates.

**Versus Merge-Proof.**
- *They do better:* actually executing the candidate's tests in an isolated boundary and reconciling claimed vs observed counts; test-integrity detectors (weakened/focused/self-fulfilling tests); merge-queue composition verification with an external dispatcher and HMAC-signed envelopes; webhook idempotency/recovery design (lost-create recovery, one-hour timeout, re-run with permission check, `index.mjs:535-600,660-830`); public read-only PR receipt with continuity states; signed receipts and Sigstore attestation; deployment-protection-rule integration; a written threat model and honest commercial gates.
- *Merge-Proof does that they do not:* test-merge-ref selection with parent matching for ordinary PRs; two matching observations; check vs run/job/step execution distinction read *from GitHub* (Vigil substitutes its own execution); approval binding to current head by a non-author with observed write permission as part of the merge decision; rulesets ∩ classic protection intersection and bypass awareness; remote ref durability; actor classification; a merge ledger row written at merge time; own-check exclusion.
- *They could copy in days:* head-bound non-author approval with permission lookup (they already call `/collaborators/{u}/permission` for re-runs); reading `/rules/branches/{b}` to report required contexts and bypass actors; reading workflow jobs/steps for the check runs they observe; `merge_commit_sha`/test-merge parent check.
- *Merge-Proof could copy in days:* app-slug-keyed latest-check selection; `NON_PROVING` reason codes in the receipt (`checks-neutral-or-skipped`, `check-timestamp-missing`, `source-coverage-incomplete`); the public read-only `vigil check <url>` receipt with `allowsProtectedAction:false`; the one-hour "NOT CHECKED on timeout" completion; delivery-ID idempotency and lost-POST recovery discipline; JSON Schemas per receipt version.
- *Significant engineering for them:* nothing architectural blocks them from exact-candidate integrity — they already own an App, a check identity and a queue path. What would take real work is the *observation model* (two matching complete observations, durability) and the rules intersection; their focus is elsewhere (test execution/agent claims), and the codebase is very large for one author.
- *Problem solved:* declared policy + **executed** evidence on the exact head/composed head, with claim reconciliation. Partially exact-candidate (merge groups yes, PR test-merge no). Closest genuine competitor in spirit; the largest gap is that its trust in GitHub-side checks and approvals is deliberately thin because it prefers to run the evidence itself.

## 4. LetItLoop — sdageltc/letitloop-action

**Versus Merge-Proof.** Nothing here is adjacent to merge integrity. What Merge-Proof could copy: nothing beyond the (cheap) idea of an HMAC-keyed proof id, which Merge-Proof's ledger row already supersedes. Problem solved: self-declared AST/WAL integrity of an agent's own artifacts. Not exact-candidate integrity, not declared-policy evidence either.

Verify names both as not checked" (`attest.go:56-62`) — an explicit notChecked list, the same discipline as Merge-Proof.
Trust model: requirements and proofs are authored in the repository (`.shipproof/`), so the PR under evaluation can edit the proof commands that evaluate it; the action does not pin them to base. No reads of checks/reviews/rulesets; head identity is the event head, no merge-ref selection; unsigned local packs are labelled "not audit-grade".
Versus Merge-Proof: they do better on evidence *packaging* (in-toto statement, keyless signing, HTML change report, jargon-free verdict block with tested word bans `verdict.go:36-55`); Merge-Proof does everything about GitHub merge state that they do not. Merge-Proof could copy in days: the explicit "claimed vs observed vs human" check taxonomy and the in-toto/DSSE envelope for the ledger row. They could copy in days: reading policy from base. Significant for them: hosted App and observation model. Problem solved: declared-policy/requirements traceability.

### 6a. gittuf/github-app

## Copyability assessment

**What competitors could take from Merge-Proof in days (cheap, API-level):**
1. Head-contains-base and `merge_commit_sha` parent check — one `GET /compare` and one commit fetch. mergeproof and Agent Vigil could add this to their head-SHA logic immediately.
2. Reviewer write-permission lookup and non-author rule — mergeproof has `exclude_author` and the review `commit_id`; adding `/collaborators/{u}/permission` is ~20 lines. Agent Vigil already calls that endpoint for re-run authorisation.
3. Rulesets ∩ classic protection read — mergeproof's `doctor.required_contexts` already does the two calls; moving it into the gate and adding `bypass_actors` is small. source-tool has the reference implementation.
4. Skipped/neutral naming in messages and reason codes.

**What would take them significant engineering or research:**
1. The **observation model** (two matching complete observations, durability of the remote ref, and STALE/UNAVAILABLE as first-class results) requires a hosted process with state and retries. mergeproof is a stateless CLI in someone else's workflow; ShipProof and LetItLoop have no GitHub read path at all. Agent Vigil has the Durable-Object plumbing and could get there, but it is oriented around executing tests, not observing GitHub.
2. **Execution proof from GitHub** (workflow run → jobs → steps on the exact SHA, treating a skipped step as no proof) — nobody in this set reads jobs/steps for the merge decision; Agent Vigil reads jobs only for post-merge outcome evidence.
3. **Test-merge-ref selection with parent matching** — only Merge-Proof does it; Agent Vigil handles composed heads only through merge groups; gittuf substitutes a git-level mergeability re-check.
4. **Actor classification** and **own-check exclusion** are simple in code but require the app identity and the rules read to be in place first.
5. An **immutable merge ledger** written at merge time by an App — mergeproof's receipt branch is the nearest and is mutable.

**What Merge-Proof could copy or improve in days:**
1. From mergeproof: `replay` against merged PRs (`replay.py`) to show what would have been NOT_PROVEN; `doctor`-style install audit; file-level review comments synced by marker; `/verified <sha7>` as an optional lightweight human attestation next to formal approval; JUnit/rdjson renderings for existing reporters.
2. From Agent Vigil: app-slug-keyed latest-check selection; explicit reason codes (`checks-neutral-or-skipped`, `check-timestamp-missing`, `source-coverage-incomplete`); a read-only public `check <PR URL>` mode whose receipt carries `allowsProtectedAction:false`; the one-hour queued-check timeout to a terminal NOT CHECKED; JSON Schemas per receipt version; the lost-POST recovery rule ("a lost POST response is not permission to create or execute a second time", `index.mjs:535`).
3. From gittuf: record approver `login+id`, base commit and target tree in the ledger row; re-evaluate open PRs when the base branch moves.
4. From source-tool: filter required checks by `integration_id`, record "control active since" timestamps for the rules that were intersected, and use `/activity` as a corroborating actor/durability source.
5. From pr-completion: a bucket/state coherence table for check rollups and recommending `--match-head-commit` in the receipt's next-action text.
6. From ShipProof (alternayte): the in-toto statement + keyless signature envelope for the ledger row, and the "claimed vs observed vs human" evidence taxonomy with a tested jargon ban in the human-facing verdict.

**Net positioning.** mergeproof, ShipProof and LetItLoop are *declared-policy* tools: the repository (and therefore, in two of three cases, the PR) says what counts as proof, and the tool checks that the declaration is satisfied. Agent Vigil is *executed-evidence* on the exact head with strong policy anchoring and a real queue story, but it treats GitHub-side approvals and checks as secondary and does not resolve the merge candidate for ordinary PRs. gittuf and source-tool are *attestation* systems for approvals and branch controls, complementary rather than competitive. pr-completion is an agent-side consumer of GitHub's own verdict. None of them currently answers Merge-Proof's question — "is the exact thing GitHub would merge right now proven, by whom, under which enforced rules, and is that observation still current" — and the parts that would close the gap (observation model, execution proof, candidate selection, rules intersection, ledger) are the parts that take weeks, not days.

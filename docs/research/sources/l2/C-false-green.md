# C. False-green / false-NOT_PROVEN adversarial review of the hosted proof engine

Scope: the repository (branch `claude/merge-proof-deep-research-czjemw`), read-only, 2026-09-19. Modules exercised with synthetic captures: `github/proof.js`, `github/collect.js`, `github/rules.js`, `github/policy.js`, `github/check.js`, `github/service.js`, `github/ledger.js`, `github/actors.js`, `github/receipt.js`, `src/analyze.js`. No network was contacted; every collector run used `github/test/fixtures.js` `fixtureFetch` through the real `Client`.

Scratch scripts (all runnable with `node <path>`; outputs saved beside them as `*.out`):

- `docs/research/sources/l2/falsegreen/proof-scenarios.js` (scenarios 0–16, earlier attempt, reused)
- `docs/research/sources/l2/falsegreen/service-scenarios.js` (A–E, service/webhook level, reused)
- `docs/research/sources/l2/falsegreen/falsegreen2.js` (F1–F12, new)
- `docs/research/sources/l2/falsegreen/freshness-noise.js` (G1–G4, new)

The question asked throughout: under what conditions does the current implementation return `verdict: VERIFIED` with `freshness.state: CURRENT` while the evidence a reasonable buyer believes that represents is incomplete; and conversely, where does it return NOT_PROVEN, STALE or UNAVAILABLE for a change GitHub itself would consider fully validated. Severity is rated against the product's own claim ("the required checks demonstrably ran against this exact version", `wording.js:33-37`).

Bottom line up front:

1. There are two genuine false-green paths, both in `ciEvidence` (`proof.js:53-118`): (F1) a PR-authored workflow whose job name collides with the required check name wins by check-run id ordering and is counted as recorded execution, and (F2) any later run of the same workflow on the same SHA (manual dispatch, schedule, re-run of an edited workflow) wins the same way because the run `event` is never collected. Both are VERIFIED/CURRENT today.
2. The engine is otherwise strongly fail-closed, to the point that large classes of ordinary repositories can never reach VERIFIED: any non-Actions CI, any commit-status CI, any behind-base PR, any CODEOWNERS/last-push requirement, any of ~15 ruleset rule types unrelated to CI/review evidence, any repository with >20 workflow runs on a SHA, any PR with a review from an account whose permission read fails, and any PR whose `mergeable` field is still being computed on the first of the two observations.
3. Currentness is coarse (any repository event stales every receipt in the repository) and has a liveness failure mode in active repositories under enforcing policy; and org-level `repository_ruleset` deliveries are rejected outright, so an org ruleset edit never stales anything.

## 0. Confirmation of the four lead-verified facts

**Fact 1 (behind-base PR can never be VERIFIED with Actions-only CI).** Confirmed by `proof-scenarios.js` scenario 1 and 16 and by the real collector in `service-scenarios.js` E: `target.kind = PR_TEST_MERGE`, `sha = M`, all checks on `H`, `ci.required[0].state = OTHER_SHA_OR_STATUS_ONLY`, `acceptedCount = 1`, verdict NOT_PROVEN. Mechanism: `collect.js:255-278` selects the test-merge commit as target whenever `git.value.mergeBase !== i.baseSha`; `proof.js:83` computes `exact = latest(named, targetSha)`; `collect.js:346-349` lists `actions/runs?head_sha=<target>` which for a `pull_request` event is the PR head, not `refs/pull/N/merge`. `accepted` (`proof.js:69-82`) is computed on `acceptanceSha` which falls back to the head, so `acceptedCount` is full while `executionCount` is 0. Classification: **documented policy, but over-strict relative to GitHub** — with `strict: false` GitHub merges this PR; the `strict` flag is collected (`rules.js:58,80`) and never consulted in `proof.js`. The receipt explains it reasonably ("The required validation result was recorded against another version", `wording.js:190-197`), but that wording tells the user the tick came from "a different commit than the one that would merge", which is misleading when Actions cannot attach a `pull_request` run to the merge commit at all; the only remedy the user actually has is "update branch" (re-point head so `mergeBase === baseSha`), which the wording does not say.

**Fact 2 (every event stales every receipt in the repository and re-queues every tracked PR).** Confirmed at `service.js:501-511` (revision bump + STALE for every receipt with matching `repositoryId`, regardless of PR) and `service.js:533-560` (queue push for every subscription in the repository). `service-scenarios.js` A shows a `merge_group` event for PR 1's group attaching PR 1's group to PR 2's subscription and queueing both. Quantification in `freshness-noise.js` G4: one proof costs 38 GitHub requests in the minimal fixture (19 per observation, two observations), more with additional reviewers (one `/collaborators/{u}/permission` call each, per observation), check-run pages, and workflow runs (one `jobs` call per run per observation). With 100 tracked PRs (the cap, `service.js:518`) a full re-proof cycle is ≥3,800 requests, i.e. ≥46 minutes at the 5,000/h installation budget, serialized through a single `busy` lock (`service.js:149-157`, `drain` processes one job per call). Any event that arrives during those 46 minutes re-stales every receipt again (`revision` mismatch → `EVENT_DURING_COLLECTION`, `service.js:194-198`, demonstrated in `service-scenarios.js` C: a VERIFIED receipt is stored with `current.state = STALE` and the enforcing gate evaluates to `failure`). Under an enforcing preset `retractChecks` (`service.js:604-624`) rewrites every stale check to `failure` before each re-proof, so in a repository with more than one event per proof-duration every required Merge Proof check in the repository oscillates or sits at `failure`. This is a liveness failure, not a safety failure, but it is the failure that gets an enforcing installation uninstalled.

**Fact 3 (ledger binding by commit SHA only).** Confirmed at `ledger.js:39-40`: `bound = headBound && mergeCommitSha && receipt.summary.target.value.sha === mergeCommitSha`. `proof-scenarios.js` 14: squash → `PROOF_BOUND_TO_PR_HEAD_ONLY`, merge-commit → `PROOF_BOUND_TO_PR_HEAD_ONLY`, only landed SHA == head → `PROOF_BOUND_TO_MERGED_STATE`. GitHub's rebase-merge rewrites committer metadata, so even rebase merges get new SHAs; the "bound to merged state" state is reachable in practice only for merge-queue groups where the group head is fast-forwarded. No tree-SHA comparison is attempted although `/repos/{r}/commits/{sha}` returns `commit.tree.sha` and is already fetched at `collect.js:203-204`.

**Fact 4 (execution rows lack `event`, `path`, blob).** Confirmed at `collect.js:361-385` and `falsegreen2.js` F2 (`row_keys` printed; `has_event=false`). The REST `workflow-run` schema in the saved OpenAPI (`rest-fpt.json`) carries `event`, `path`, `head_branch`, `pull_requests[]`, `referenced_workflows[]`, `run_started_at`, `head_repository`; the `job` schema carries `workflow_name`, `head_branch`, `created_at/started_at/completed_at`, `runner_*`. None is retained.

## 1. Target selection edge cases

**1a. Stale test-merge ref.** `collect.js:262-278` requires `refs/pull/N/merge` to point at `merge_commit_sha` and that commit's parents to be exactly `[baseSha, headSha]`; otherwise `TEST_MERGE_NOT_CURRENT` → target UNAVAILABLE → `APPLICABLE_MERGE_STATE_UNAVAILABLE` + `CURRENT_STATE_EXECUTION_NOT_PROVEN` gaps → NOT_PROVEN, freshness UNAVAILABLE. Correct and fail-closed. Consequence: after any base push GitHub recomputes `merge_commit_sha` lazily; the collector's own `GET /pulls/N` triggers recomputation, so observation 1 frequently sees the old value and observation 2 the new one → `CHANGED_DURING_COLLECTION`. The queue retries three times (`service.js:761-766`) and then marks the subscription `UNAVAILABLE` with no further automatic attempt until the next repository event. Severity: low (false NOT_PROVEN/UNAVAILABLE, self-healing on the next event).

**1b. Base moves between observation 1 and 2, each consistent.** `identity.baseSha` is re-read per observation (`collect.js:113-115`); `hash(first) !== hash(second)` → STALE, `EVIDENCE_CHANGED_DURING_COLLECTION` gap → NOT_PROVEN. Correct.

**1c. Base moves after observation 2, before the check is published.** Nothing inside `run()`/`publish()` re-observes. The receipt is CURRENT at issue; the subsequent `push` webhook (if delivered) stales it and `retractChecks` rewrites the published check. If the webhook is not delivered (GitHub does not automatically redeliver failed deliveries), the published `success` on the head SHA stays valid for GitHub's required-check evaluation forever. This is inherent to the Checks API; the mitigation the engine lacks is any periodic reconciliation (no timer-driven refresh exists; `drain` only services the queue). Severity: medium; fix strengthens core.

**1d. Merge-group selection.** `collect.js:206-254` binds the group head via `git/ref`, ancestry via two `compare` calls, and the live queue entry via GraphQL `mergeQueueEntry` with state in `AWAITING_CHECKS|MERGEABLE|LOCKED`; `proof.js:220-229` re-checks `selection` against `identity`. `falsegreen2.js` F11: check + job on the group SHA, approval on the head → VERIFIED, and `check.subjects` publishes on both SHAs. Sound. The service-level defect (fact 2) is that the group from a `merge_group` event is attached to *every* subscription in the repository (`service.js:533-545`); for the wrong PR the collector correctly refuses (`CANDIDATE_NOT_IN_GROUP`, `service-scenarios.js` B) but the queue still spends a full collection and the receipt store gets a NOT_PROVEN receipt for a PR that is not in the queue, and its previously CURRENT receipt is superseded. And `mergeGroup` is reset to `null` for every subscription on any non-`checks_requested` `merge_group` action (`destroyed` for another PR's group clears this PR's group). Severity: medium (false NOT_PROVEN, wasted budget); fix strengthens core (route the group only to the PR whose head is in `merge_group.head_ref`/via `pull_requests` on the group's runs, or key on the group SHA).

## 2. Check evidence

**2a. FALSE GREEN — same-app duplicate names decided by check-run id (F1).** `proof.js:53-56` filters `named` by name and (optionally) appId; `proof.js:61-62` `latest` picks the highest id on the target SHA; `proof.js:91-93` `ambiguous` only fires when two *different apps* posted the name on the target. GitHub Actions is a single app (15368), so two workflows that both define a job named `test` are never ambiguous. Reproduction (`falsegreen2.js` F1): rule `{context:"test", app_id:15368}`; workflow 30's `test` check id 10 FAILED with a failed step; PR adds `.github/workflows/fake.yml` (workflow 31) whose job `test` produced check id 11 success with one step; execution rows for both. Result: `VERIFIED`, `freshness CURRENT`, `checkId=11`, `chosen_workflowId=31`, `local_findings=[]`, only a `PROTECTED_BOUNDARY_ADVISORY` (the `ci-deploy` category is advisory in `src/rules.js`). Expected semantics: the required check must be satisfied by the workflow the repository intends; at minimum, two same-name check runs from different workflows on the target SHA with divergent conclusions are ambiguous, and a workflow file added or modified by the candidate itself is not independent evidence. GitHub's own required-check evaluation also takes the latest check run with that name, so GitHub would merge — but Merge Proof's claim is stronger than GitHub's ("demonstrably ran"), and the `workflowId` needed to detect this is already in the execution rows. Severity: **high** (exploitable by any PR author on a `pull_request`-triggered workflow; the only GitHub-native defence, the `workflows` ruleset rule, is classified unsupported by `rules.js:86-89` and blocks VERIFIED). Fix strengthens core: extend `ambiguous` to `new Set(named-on-target.map(x => execution-row.workflowId ?? x.appId)).size > 1`, and treat `candidateFiles ∩ {path of the workflow that produced the accepted job}` as a blocking gap (`WORKFLOW_MODIFIED_BY_CANDIDATE`) rather than an advisory.

**2b. FALSE GREEN — later run of the same workflow, trigger unknown (F2).** Same mechanism with the same `workflow_id`: pull_request run → check id 10 failure; a later run on the same `head_sha` (workflow_dispatch on the branch, schedule on the branch, `re-run` after a force-push of the workflow file with the same SHA is not possible, but dispatch is) → check id 12 success. `falsegreen2.js` F2: VERIFIED. The run `event` is not collected (fact 4), so the receipt cannot even display which trigger produced the accepted evidence. Whether GitHub counts dispatch runs toward required checks (the lead states it ignores them) does not matter for the buyer: the receipt says "EXECUTION_RECORDED" for a run whose inputs are unknown. Severity: **medium-high** (requires write access to the branch or Actions dispatch rights; dispatch inputs can disable steps). Fix strengthens core: record `event`, `head_branch`, `pull_requests[].{number, head.sha, base.sha}` from the run; accept only `pull_request`/`merge_group` (and `pull_request_target` never) for the target; flag any accepted job whose run `event` is not in that set.

**2c. Rule bound to app A, app B fails the same name (F3).** Filtered out by `x.appId === rule.appId` → VERIFIED. Matches GitHub's semantics (a bound required check ignores other apps). Documented policy; low. The reverse (F3b: rule appId null, two apps disagree) is correctly `ambiguous` → NOT_PROVEN. Note the asymmetry: `ambiguous` compares apps, not conclusions, so two apps both succeeding is also NOT_PROVEN — a false NOT_PROVEN for repositories that mirror CI (e.g. Actions + a second CI app posting the same context) with a null-bound rule. Low.

**2d. Non-Actions apps and commit statuses can never be VERIFIED (F3c, F3d).** `executed` requires exactly one execution row whose `checkId` equals the accepted check (`proof.js:84-88, 97`), and execution rows come only from `/actions/runs` (`collect.js:346`). A CircleCI/Buildkite/Jenkins/GitLab-mirror check run → `SUCCESS_ASSERTED_EXECUTION_UNAVAILABLE`; a commit status → `OTHER_SHA_OR_STATUS_ONLY` (there is no `exact` for statuses at all). Both NOT_PROVEN with `acceptedCount` full. This is a documented product decision ("GitHub-reported execution") but a reasonable buyer reading "required checks" will not expect their non-Actions CI to be structurally incapable of proof. Severity as a false-NOT_PROVEN: **high** for market coverage, low for safety. The remediation text ("Run the required validation against the current version", `wording.js:36`) is wrong for this case — the validation did run on the current version; what is missing is an Actions job record, which no action by the user can create. Fix expands product (accept app-level evidence with a distinct, weaker state) or at least strengthens wording.

**2e. skipped / neutral at job vs step; continue-on-error.** Check conclusion `skipped`/`neutral` → state `SKIPPED`/`NEUTRAL`, `accepted = true`, `executed = false` → NOT_PROVEN (F9). GitHub counts a required check concluded `skipped`/`neutral` as passing (`check.js:9-10` says so). Over-strict but correct for the product's claim; documented. A skipped *step* inside the required job (an `if:` step) → `SUCCESS_ASSERTED_EXECUTION_UNAVAILABLE` (`proof-scenarios.js` 4): every step must be `success` (`proof.js:104-107`). A job with `continue-on-error: true` on a failing step reports the step as `failure` in the API and the job `success`; the engine rejects it — good. But a routine `if: github.event_name == 'push'` step (very common: publish/deploy steps) makes the whole repository permanently NOT_PROVEN. Severity: **medium false NOT_PROVEN**, and the receipt's `next` text does not mention skipped steps. Fix strengthens core wording; a policy question whether `skipped` steps with `success` job should count.

**2f. Cancelled then re-run (`run_attempt > 1`).** `collect.js:355-357` reads only `attempts/{run_attempt}/jobs`. On "re-run failed jobs" the new attempt's jobs list includes the re-run jobs with new ids and check runs with new ids; `latest` by id picks them. `proof-scenarios.js` 6: VERIFIED with `attempt = 2` retained in the row but not surfaced anywhere in the human receipt, and no gap. Information ignored: the failing attempt 1 (flaky-test masking). Low; fix expands product (surface attempt history).

**2g. Unrelated job failure in the same run.** `runConclusion === 'success'` is required (`proof.js:101`), so a run where a non-required job failed (matrix leg, docs job) → NOT_PROVEN (`proof-scenarios.js` 8). GitHub would merge if only the required job passed. Over-strict; medium false NOT_PROVEN; documented nowhere in wording.

**2h. `jobs.length === 1`.** Zero jobs is the F3c case. Two execution rows with the same `checkId` are impossible (one check run per job) except across attempts, which are not both read. The condition is effectively "exactly the Actions job that owns this check run". Fine.

**2i. Reusable workflows.** A `workflow_call` job's check run name is `caller-job / callee-job`; the rule must be configured with that name, and the job appears under the caller run, so the mapping works. Not a defect; no fixture needed.

**2j. Workflow-run cap.** `assert(runs.length <= 20, "WORKFLOW_LIMIT")` (`collect.js:351`) — `falsegreen2.js` F10: 21 runs on the head → execution UNAVAILABLE → NOT_PROVEN and freshness UNAVAILABLE. A monorepo with path-filtered workflows routinely exceeds 20 runs per SHA (each is one run even when all jobs skip). Severity: **medium false NOT_PROVEN**, permanent for such repositories. Related caps: `REVIEWER_LIMIT` >30 distinct reviewers (`collect.js:393`), `PAGINATION_LIMIT` at 500 rows (`client.js:57-70`), `compare` files ≥300 → `INCOMPLETE_GIT_METADATA` → local FAIL → verdict FAIL (`local-evidence.js:223-238`, `proof.js:250`).

## 3. Approvals

`approvalEvidence` (`proof.js:151-206`) keeps the latest `APPROVED|DISMISSED|CHANGES_REQUESTED` per user, then counts `current` = APPROVED ∧ `sha === headSha` ∧ `userType === "User"` ∧ not the PR author ∧ write permission observed true.

- **commit_id vs head.** Approvals on an older head are excluded even when `dismissStale` is false and GitHub would count them. Documented ("Old-head approvals are conservatively insufficient", README:152). False NOT_PROVEN by design; low.
- **Permission at observation, not at review time.** `collect.js:397-411` reads `/collaborators/{login}/permission` now. A reviewer demoted after approving → NOT_PROVEN; a reviewer promoted after approving → PROVEN although the approval was given without write. The second direction is a (minor) evidence-trusted-too-strongly case; GitHub evaluates the same way, so low.
- **DISMISSED / COMMENTED.** F12: approve then comment keeps the approval; a DISMISSED latest state removes it. Correct.
- **Bot approvals excluded (F7).** A GitHub App with write that approves (GitHub counts it toward required approvals) yields `INSUFFICIENT_CURRENT_HUMAN_APPROVAL` with `current=[]`. The gap text (`wording.js:52-57`) says "not carry the approvals your repository requires … approved by an eligible reviewer other than the author"; it never says that App/bot approvals are deliberately excluded, so an owner whose repository permits bot approvals sees a false NOT_PROVEN with an explanation that does not match. Copilot code review cannot approve, so the "Copilot approval" case does not arise; but the ruleset rule type `copilot_code_review` is treated as unsupported (`rules.js:86-89`; F8) and therefore any repository that turns on automatic Copilot review through a ruleset can never be VERIFIED. Severity: medium false NOT_PROVEN with misleading wording; fix strengthens core (name the exclusion in wording; treat `copilot_code_review` as not-evidence-relevant rather than unsupported).
- **Author via co-author.** `proof-scenarios.js` 3: an approver who authored commits inside the PR (not the PR opener) counts → VERIFIED. GitHub does the same. Information ignored: `actors.commits[].author` is already collected and could produce a `REVIEWER_AUTHORED_COMMITS` advisory. Low.
- **Required count.** `Math.max` across classic and rulesets (`rules.js:42`); both apply simultaneously on GitHub, so max is right.
- **lastPush / codeOwners → fail closed.** `proof.js:180-187`: any `require_last_push_approval` or `require_code_owner_review(s)` → `CODE_OWNER_APPROVAL_UNAVAILABLE` / `LAST_PUSH_ACTOR_APPROVAL_UNAVAILABLE` regardless of observed approvals (F8b: NOT_PROVEN). Consequence: **every repository with CODEOWNERS review required can never be VERIFIED**, and `setup.js:223-225` also reports the gate NOT_READY. Documented, but this is the single most common approval setting in organizations that would pay for an enforcing gate. Severity: high false NOT_PROVEN for coverage; fix expands product (CODEOWNERS resolution needs Contents read of `CODEOWNERS` + team membership, which Merge Proof already partially has).
- **CHANGES_REQUESTED from a non-write user.** `proof-scenarios.js` 9: a `CHANGES_REQUESTED` by an account with `writePermission=false` → `CHANGES_REQUESTED_OBSERVED` → NOT_PROVEN. GitHub only blocks on change requests from users whose review would count. Over-strict; a drive-by read-only account can block VERIFIED on a public repository forever (until dismissed by a maintainer). Severity: medium (denial-of-proof on public repos). Fix strengthens core: require `writePermission.value === true` for the block as well.
- **Approvals on a merge-group target.** Reviews are bound to `identity.headSha`; the group SHA is irrelevant; F11 VERIFIED. Correct.
- **Ghost reviewer (F6 / scenario 11).** Any review (even COMMENTED) whose author's permission read fails (deleted user → 404; suspended; outside collaborator removed) makes `reviews` contain a nested UNAVAILABLE. `proof.js` still returns VERIFIED, but `freshness.state = UNAVAILABLE` (`proof.js:270-284` uses `hasUnavailable`, which recurses), `collectionComplete` is false (`service.js:199-216`), the trial does not start, and an enforcing gate emits `failure` with `CURRENTNESS_UNAVAILABLE`. There is no way for the user to fix this short of the ghost review disappearing. Severity: **high liveness** on any long-lived PR in an org with churn; fix strengthens core (treat permission-unavailable as "not eligible" for that reviewer rather than poisoning the whole capture, and exclude it from `hasUnavailable`).

## 4. Rules

- **`strict` collected, unused.** `rules.js:9,58,80` set `out.strict`; nothing reads it. Target selection makes it moot only in one direction: with `strict=false` GitHub merges a behind-base PR while the engine says NOT_PROVEN (`proof-scenarios.js` 16). Documented policy; the receipt could say "your repository does not require the branch to be up to date; Merge Proof does".
- **`evaluate` enforcement.** OpenAPI description of `GET /repos/{o}/{r}/rules/branches/{b}` (saved `rest-fpt.json`): "Rules in rulesets with 'evaluate' or 'disabled' enforcement statuses are not returned." Evaluate-mode rules are therefore invisible and cannot block. Correct for "what GitHub enforces"; information ignored for "what the org intends".
- **Org rulesets.** Returned by the same endpoint regardless of level (same description) with `ruleset_source_type`; collected (`collect.js:93-101`). Good. Bypass actors are not on this endpoint and are never read (see §13).
- **Unsupported types.** `rules.js:86-89` marks *every* type other than `deletion|non_fast_forward|creation|required_status_checks|pull_request|merge_queue` unsupported and `proof.js:236-237` turns that into a blocking gap. F8 enumerates: `update`, `workflows`, `code_scanning`, `branch_name_pattern`, `required_deployments`, `copilot_code_review`, `max_file_size` → NOT_PROVEN. The OpenAPI rule union has 23 types; 17 block VERIFIED. Several are ubiquitous in org rulesets (`update` = "restrict updates", `branch_name_pattern`, `commit_message_pattern`, `file_path_restriction`, `max_file_size`) and have nothing to do with the evidence claim. The receipt says "The repository requirement 'update' cannot be established by Merge Proof" (`setup.js:171-173`), which is technically true and practically meaningless to an owner. Severity: **high false NOT_PROVEN for coverage**. Fix strengthens core: classify rule types as evidence-relevant (require proof), push-time (`update`, patterns, file restrictions — GitHub already enforced them at push, irrelevant to merge evidence), or genuinely unsupported (`required_deployments`, `required_signatures`, `code_scanning`, `workflows`, `required_linear_history`).
- **`required_signatures` / `required_linear_history` / `required_deployments`.** Unsupported → NOT_PROVEN (classic: `rules.js:54-55`; rulesets: default branch). Confirmed. Note the collector already records per-commit `verification.verified` (`collect.js:433-434`), so `required_signatures` could be proven for the PR commits (not for the future merge commit).
- **Merge queue.** Field names match the REST schema (`grouping_strategy` ∈ {ALLGREEN, HEADGREEN}; `merge_method`, `max_entries_to_build` … exist and are ignored). ALLGREEN → unsupported → NOT_PROVEN (F8b). HEADGREEN before a group exists → VERIFIED with `queueStage = ADMISSION_ONLY`, `notChecked` includes `MERGE_QUEUE_GROUP_NOT_YET_PROVEN`, enforcing title "VERIFIED · PR evidence satisfied · queue group proof still required" and the check is published `success` on the head (F8b). That is an **ambiguous state**: a `success` required check on the head is exactly what admits the PR to the queue; the group-stage proof is a second check on the group SHA that GitHub only waits for if the same check name is required on the group — which it is, so the design holds, but only if the group proof runs before the queue's `check_response_timeout_minutes` (ignored by the engine) elapses; under the fact-2 noise pattern this is not assured.

## 5. Base drift and the local analyzer through hosted metadata

- The hosted path can only reach VERIFIED with `target.kind ∈ {HEAD_CONTAINS_CURRENT_BASE, MERGE_GROUP, PR_TEST_MERGE-with-checks-on-M}`. In the first case drift is zero by definition; in the other two the validated commit contains the current base. So the "base moved without overlap → VERIFIED" policy in `src/analyze.js:183` is **never the deciding factor in hosted proofs**; it only matters for the CLI.
- **FALSE NOT_PROVEN — drift blocks even when the combined state was validated (F4).** mergeBase ≠ base, overlapping file, checks and job recorded on the test-merge commit `M` → `ci.state = PROVEN` but `BASE_DRIFT_UNVERIFIED` is pushed by `proof.js:246-248` ("Remote CI does not silently waive … BASE_DRIFT_UNVERIFIED"). The finding's own text says the missing evidence is "A validation run of the candidate combined with the current base" — which is precisely what `EXECUTION_RECORDED` on `M` (parents `[base, head]`, `collect.js:269-273`) is. Severity: medium (only reachable by non-Actions/`merge_group`-style evidence on M, or Actions `merge_group` targets — for MERGE_GROUP targets the same contradiction applies: group SHA contains base, yet drift still blocks). Fix strengthens core: waive `BASE_DRIFT_UNVERIFIED` when `ci.state === PROVEN` and `target.kind ∈ {PR_TEST_MERGE, MERGE_GROUP}`.
- **Compare limits.** `x.files.length < 300` (`collect.js:170`) → 300-file PRs are `INCOMPLETE_GIT_METADATA` → local FAIL → verdict FAIL → enforcing `PROOF_COULD_NOT_COMPLETE`. Correct fail-closed; large-PR limitation not stated in wording.
- **Renames.** `filename` only; `previous_filename` ignored (`collect.js:176-182`). Overlap is by exact path so a base-side rename of a candidate-touched file is missed (`proof-scenarios.js` 7). Irrelevant for hosted verdicts per the first bullet; relevant for the CLI.
- **Ignore lists not loaded.** `src/analyze.js:148-150`: hosted callers get `rules: []`, so `.mergeproofignore` is never consulted; `PROTECTED_BOUNDARY` fires for every migration/auth/billing path with `doNext` text that tells the user to "re-run with an exclusion … (see .mergeproofignore.example)" (`analyze.js:217`) — advice that cannot work in hosted mode. Under `REPOSITORY_REQUIREMENTS` the gap is non-blocking (scenario 13: check `success`, title "NOT_PROVEN · merge requirement satisfied"); under the boundaries preset it requires two approvals. Severity: low-medium (misleading wording, ambiguous title).

## 6. Currentness

- **What invalidates.** Any of twelve event types for the repository (`service.js:476-489`) stales every receipt (§0 fact 2). `check_run`/`check_suite` from Merge Proof's own app are ignored (`service.js:429-438`). Events not subscribed: `member`, `team`, `organization` (permission changes), `pull_request_review_comment`, `pull_request_review_thread`, `workflow_job`. So a reviewer losing write access never stales a receipt; but since `read()` never presents a saved CURRENT as live (`service.js:339-347`) and the published check is only rewritten on events, the published `success` check persists.
- **Webhook loss.** No reconciliation loop, no periodic re-observation, no use of `X-GitHub-Delivery` gap detection. See §1c. Severity medium.
- **Org-level `repository_ruleset`.** OpenAPI `webhook-repository-ruleset-{created,edited,deleted}`: `required: [action, repository_ruleset, sender]`; `repository` is optional and absent for organization rulesets. `service.js:439-447` asserts `repoName(p.repository.full_name)` → `INVALID_WEBHOOK_SCOPE` thrown → HTTP 403 (`http.js:453`) → GitHub records a failed delivery, nothing is staled, nothing re-queued (`service-scenarios.js` D). **An org admin can remove a required check, add a bypass actor, or drop the approval count from an org ruleset and every CURRENT receipt and every published `success` check in every repository stays as is** until some unrelated repository event arrives. Severity: **high** (silent invalidation of the rules the proof was computed against). Fix strengthens core: accept org-level deliveries and stale every receipt for every subscription under that organization (or, without org mapping, all receipts).
- **CODEOWNERS / workflow changes on base.** Arrive as `push` → staled. Fine.
- **False STALE (G1–G3).** `freshness()` hashes nine whole sub-objects. Any new check run of any name on the head (G1), any COMMENTED review (G2), any change in `identity.githubMergeState` (`"clean"` → `"unstable"` → `"blocked"`, which GitHub flips as checks come and go) (G3) → STALE → "RE-PROOF REQUIRED" → under enforcing policy the published check is rewritten to `failure` (`policy.js:171-173`) until the re-proof lands. None of those changes can alter the verdict. Severity: medium (noise + liveness); fix strengthens core (hash the evidence actually consumed: required check rows, statuses for required names, execution rows for accepted checks, review rows with state ∈ {APPROVED, DISMISSED, CHANGES_REQUESTED}, rules, target, remote, git; exclude `githubMergeable`/`githubMergeState`).

## 7. Actors

- Classification is the account `type` field only (`actors.js:134-145`); `[bot]` suffix corroborative. Merge actor is taken from the webhook `merged_by` (`service.js:595`) — an unverified payload field that is also not cross-checked against `GET /pulls/N` later. `agentIdentity` is derived from authorship only (PR author + commit author/committer), never from reviewers, workflow actors or check publishers (`actors.js:224-246`, by design). A Copilot coding-agent PR is authored by `copilot-swe-agent[bot]` and is detected; a Claude Code/Cursor/Codex session using the user's token is recorded as the human (stated limitation, `actors.js:175-176`). `review.author_association` and commit `Co-authored-by` trailers are ignored (the latter deliberately: no free text). No false green here; the receipt's `NONE_OBSERVED` text is careful.

## 8. Ledger

- `recordMerge` (`service.js:566-603`) trusts webhook `head.sha`, `merge_commit_sha`, `merged_at`, `merged_by`. The webhook is HMAC-verified (`service.js:362-366`) so the source is GitHub, but the PR object in the payload is a snapshot at delivery; `merge_commit_sha` is present for merged PRs and correct in practice. No tree comparison (fact 3). `chosen` is the latest receipt issued before `merged_at` whose head matches, else the latest receipt at all — so a squash merge of a PR whose last receipt was NOT_PROVEN on an older head is recorded as `PROOF_BOUND_TO_OTHER_STATE` with that older verdict; correct and explicit. `currentnessAtMerge` is always UNAVAILABLE (`ledger.js:55-59`): the ledger never claims decision-time currentness. Sound; the limitation is that in squash/merge-commit repositories the ledger's headline `boundToMergedState` is false for every row, which a buyer will read as "Merge Proof never proved what merged".

## 9. Check publication mapping

`policy.evaluate` (`policy.js:98-153`): advisory → `success` only for VERIFIED+CURRENT, else `neutral`; enforcing → `success` iff no blocking. Stale retraction → `neutral` (advisory) / `failure` (enforcing) (`policy.js:171-173`). Publication on the head and on the group SHA (`check.js:20-30`). Two ambiguous outputs:

1. Advisory NOT_PROVEN publishes `neutral`; if an admin makes the check required while still on the ADVISORY preset (the setup instructions say to switch presets, `setup.js:263`, but nothing enforces the order) GitHub treats `neutral` as passing — a required check that never blocks. `check.js:9-10` documents it; `setPolicy` refuses enforcing presets without a paid plan (`service.js:56-60`) so a trial user *cannot* make the gate real. Medium (product), documented.
2. Enforcing `REPOSITORY_REQUIREMENTS` with only `PROTECTED_BOUNDARY` → verdict NOT_PROVEN, check `success`, title "NOT_PROVEN · merge requirement satisfied" (scenario 13). Correct per policy, confusing per UX.

## 10. Two-observation consistency

`collect()` (`collect.js:522-539`) hashes the entire `collectOnce` result, excluding only the outer `startedAt/observedAt/source/consistency`. Timestamps inside (`checks[].startedAt/completedAt`, `statuses[].updatedAt`, `reviews[].submittedAt`, `steps[].startedAt`) are stable once completed. The volatile fields are `identity.githubMergeable` and `identity.githubMergeState` (`collect.js:143-144`): GitHub computes `mergeable` asynchronously and returns `null` until done, and the collector's own `GET /pulls/N` is what schedules the computation. **F5 through the real collector**: observation 1 `mergeable: null`, observation 2 `true` → `CHANGED_DURING_COLLECTION` → `EVIDENCE_CHANGED_DURING_COLLECTION` gap → NOT_PROVEN and STALE, on a PR whose evidence is otherwise perfect. The queue retries at most three times (`service.js:761`) and the second attempt usually succeeds (GitHub caches), so this presents as flakiness plus wasted budget; but on a repository under constant events every retry also trips the `revision` check. Severity: medium false NOT_PROVEN; fix strengthens core (exclude the two mergeability fields from identity or from the hash; they are GitHub's opinion, not evidence).

## 11. Trial

`meter.complete` (`meter.js:65-82`): trial starts only when `collectionComplete && current.state === "CURRENT" && verdict ∈ {VERIFIED, NOT_PROVEN}`; `collectionComplete` (`service.js:199-216`) requires verdict ≠ FAIL, `STABLE_OBSERVATION`, and every one of nine capture areas AVAILABLE with no nested UNAVAILABLE. So a FAIL or any partial capture cannot start the trial; a fully collected NOT_PROVEN (e.g. a behind-base PR, F1-type NOT_PROVEN) does start it. Consistent with the README ("first CURRENT, collection-complete VERIFIED or NOT_PROVEN"). One consequence of §3 ghost-reviewer: a repository whose only open PRs carry a ghost review can never start a trial, and the account shows AWAITING_FIRST_PROOF indefinitely.

## 12. Permissions

- Administration:read missing → `/branches/{b}/protection` returns 403 (not 404) → `classic` UNAVAILABLE (`client.js:74-81`) → `requirements` UNAVAILABLE → `RULES_UNAVAILABLE` gap; also `/collaborators/{u}/permission` (Administration or Metadata depending on account type) fails → nested UNAVAILABLE in reviews → freshness UNAVAILABLE. Verdict NOT_PROVEN, never VERIFIED. Correct.
- Merge queues:read missing → GraphQL `mergeQueueEntry` errors → `selection` UNAVAILABLE → `CURRENT_MERGE_GROUP_SELECTION_UNAVAILABLE` (`proof.js:220-229`) → NOT_PROVEN at group stage; admission stage unaffected. Correct.
- Actions:read missing → execution UNAVAILABLE → `SUCCESS_ASSERTED_EXECUTION_UNAVAILABLE` → NOT_PROVEN. Correct.
- Public-anonymous path (`authorization: PUBLIC_ANONYMOUS`) has no Actions/Administration → same. Correct.

## 13. Anything else

- **Bypass is invisible.** Neither `bypass_actors` (on `GET /repos/{r}/rulesets/{id}`), rule-suite evaluations (`/repos/{r}/rulesets/rule-suites`, which record `evaluation_result`, `rule_evaluations[].result` and bypass use), nor classic `enforce_admins` is read. A merge performed via admin bypass or a bypass actor is recorded in the ledger with whatever receipt existed. The receipt's `gateObservation` string (`ledger.js:62`) says as much, but the product cannot distinguish "gate satisfied" from "gate bypassed". Fix expands product (Administration:read already covers both endpoints).
- **`pull_request_target` / fork PRs.** Runs on `pull_request_target` have `head_sha` = base branch commit in practice and check out the base by default; they would not match the target and are therefore harmless, but no fixture can confirm the `head_sha` semantics offline. Fork PRs: `remote` reads the head repository (`collect.js:284-300`); fine.
- **Check-run `id` ordering as time.** `latest` uses numeric id (`proof.js:61-62`), which is global and monotonic; safe.
- **`filter=all`** includes reruns and cancelled runs; the highest id wins; a cancelled later attempt (`conclusion: cancelled`) after a successful earlier one → FAILED → NOT_PROVEN. Correct.
- **Own-check collision.** A rule requiring "Merge Proof exact-state receipt" bound to another app → `NAME_COLLIDES_WITH_MERGE_PROOF_CHECK` (`proof.js:41-50`); the collector drops every check run with that name (`collect.js:311`), so a hostile app cannot impersonate the receipt into the proof. Good.
- **Policy change during a run** is caught by the `revision` counter (`service.js:66-76`, `194-198`). Good.
- **`identity.merged` from `p.merged === true`** — for a closed-unmerged PR `LIVE_PR_NOT_OPEN`; for merged `HISTORICAL_…` only when `historical` requested. Correct.

## (a) Evidence trusted too strongly

1. Highest-id check run with the required name from the same app is taken as *the* required check (`proof.js:61-62, 83`), regardless of which workflow produced it or whether the candidate itself introduced that workflow (F1).
2. Any Actions run on the target SHA is accepted as execution regardless of trigger event or `head_branch` (F2; `collect.js:346-385`).
3. Reviewer write permission at observation time is treated as permission at approval time (`collect.js:397-411`).
4. Webhook `merged_by`, `merge_commit_sha`, `head.sha`, `merged_at` are recorded without a later REST cross-check (`service.js:567-600`).
5. `remote.confirmed` is a single-point `git/ref` read (documented, `proof.js:341`).
6. `verification.verified` from the commit object is recorded as "signed" without reading `verification.reason` semantics beyond the string (`collect.js:433-434`); informational only.

## (b) Information ignored

- Run `event`, `path`, `head_branch`, `pull_requests[].{head,base}.sha`, `referenced_workflows`, `run_started_at`, `head_repository` (`collect.js:361-385`).
- Job `workflow_name`, `head_branch`, `created_at/started_at/completed_at`, `runner_*`; earlier `run_attempt`s (`collect.js:355`).
- Check `started_at` relative to the head commit's push time (a check that started before the commit existed cannot have tested it; `checks[].startedAt` and `git.dates[head]` are both collected and never compared).
- Rule suites (`/rulesets/rule-suites`), `bypass_actors`, ruleset `enforcement`, `check_response_timeout_minutes`, `merge_method`, `allowed_merge_methods`.
- `strict` (§4), `dismissStale` (collected, unused beyond flags).
- PR `auto_merge`, `rebaseable`, `mergeable_state` (collected into identity but only as noise; §10).
- Review `author_association`; commit `Co-authored-by` (deliberately).
- The workflow file blob at the target (`WORKFLOW_CHECKOUT_CONTENTS` is declared not checked, `proof.js:299`).
- Compare `previous_filename` (§5).
- `CODEOWNERS` content and team membership (§3).
- Organization-level webhook deliveries (§6).

## (c) False NOT_PROVEN candidates (ranked by how many ordinary repositories they exclude)

1. CODEOWNERS or last-push approval required → never VERIFIED (`proof.js:180-187`).
2. Any non-Actions check or commit-status CI → never VERIFIED (F3c, F3d).
3. Any of 17 ruleset rule types outside `{creation, deletion, non_fast_forward, required_status_checks, pull_request, merge_queue}` → never VERIFIED (F8), including push-time rules with no evidence relevance (`update`, name/message patterns, file restrictions) and `copilot_code_review`.
4. Behind-base PR with Actions CI → never VERIFIED regardless of `strict` (scenario 1/16).
5. Required job with any `skipped` step, or any non-required job failing in the same run (scenarios 4, 8).
6. >20 workflow runs on the SHA (F10); >30 reviewers; 300+ files; >500 check runs.
7. Any review by an account whose permission read fails → freshness UNAVAILABLE forever, gate `failure` (F6).
8. `mergeable` computed between observations → CHANGED_DURING_COLLECTION (F5).
9. CHANGES_REQUESTED by an account without write (scenario 9).
10. Bot/App approvals not counted (F7) with wording that does not say so.
11. `BASE_DRIFT_UNVERIFIED` while execution is recorded on the test-merge/group commit (F4).
12. `skipped`/`neutral` required check conclusion (F9) — GitHub passes it.
13. Two apps both succeeding under a null-bound rule → ambiguous (§2c).
14. Any repository event during the ~40-request collection window → STALE (`service-scenarios.js` C), compounding under load.

## (d) Ambiguous states

- `VERIFIED` + `freshness: UNAVAILABLE` (F6, scenario 11): the receipt headline says VERIFIED; the gate says failure; the trial does not start.
- `NOT_PROVEN` + check `success` + title "merge requirement satisfied" (scenario 13).
- `VERIFIED` + `queueStage: ADMISSION_ONLY` published `success` on the head (F8b): a green required check that is explicitly not the final proof.
- `acceptedCount === required.length` with `ci.state: NOT_PROVEN` (scenario 1, F3c/F3d): the ledger's `checkEvidence.acceptedCount` reads as "all accepted".
- `current.state: STALE` with `historicalVerdict: VERIFIED` and check conclusion `failure` under enforcing policy: the check says failure, the receipt says VERIFIED, the reason is `GITHUB_EVENT:check_run` for an unrelated PR.
- `PROOF_BOUND_TO_PR_HEAD_ONLY` on every squash/merge-commit ledger row.
- Remediation text "Run the required validation against the current version" for cases where it did run (non-Actions app, behind-base Actions).

# D — Authority, Approval Binding, Actions-Run Binding, and Agent Provenance: What Merge-Proof Can Prove

Research date: 2026-09-19. Sources are the GitHub REST OpenAPI description (`api.github.com.json` and `ghec.json` copies in `scratchpad/l2/api/`), the octokit GraphQL schema (`graphql-schema.graphql`), the `github/docs` content source, the App permission mapping (`s2s-perms.json`, from github/docs `src/github-apps/data`), the org/enterprise audit-log event catalog (`audit-org.json`, `audit-ent.json`), and cited community/changelog material. Every field name below is quoted exactly as it appears in those sources. Grades: **PROVE** = GitHub asserts it and it is bound to a specific SHA/id; **OBSERVE** = GitHub asserts it now but it is not bound to the point in time of the merge; **INFER** = Merge-Proof must compute it from other facts; **NOT KNOW** = not exposed under a read-only App installation (receipt must say `NOT_PROVEN`).

Suggested standard receipt sentence for the NOT KNOW class: *"NOT_PROVEN: GitHub does not expose enough information under this installation's permissions to establish <fact>."*

## PART A — Approval and authority

### A1. Reviewer identity

REST `GET /repos/{owner}/{repo}/pulls/{pull_number}/reviews` (App permission: `pull_requests` read) returns `pull-request-review` objects with properties `id`, `node_id`, `user`, `body`, `state`, `html_url`, `pull_request_url`, `_links`, `submitted_at`, `commit_id`, `body_html`, `body_text`, `author_association`. `user` is a `simple-user` with `login`, `id`, `node_id`, `type` (`"User"`, `"Bot"`, `"Organization"`), and `user_view_type`. GraphQL `PullRequestReview.author: Actor` resolves to `User`, `Bot` ("A special type of user which takes actions on behalf of GitHub Apps"), `Mannequin`, `Organization` or `EnterpriseUserAccount`; `__typename` is the authoritative discriminator.

- The numeric `id` is the durable identity; `login` can be renamed (a user rename keeps `id`). The receipt should record both.
- The `[bot]` login suffix is a GitHub convention for the bot user created for every GitHub App (`<slug>[bot]`, `type: "Bot"`); it is reliable **as a platform marker of "this action was performed with an App installation token"**, but it says nothing about whether an AI wrote anything. A human OAuth token or PAT never produces a `[bot]` login; a plain automation script using an App token always does.
- Ambiguity: the Copilot reviewer bot is *not* consistently rendered. Community reports show requested-reviewer payloads containing `"login": "Copilot"` with `"type": "user"` in web UI JSON (community discussion #160286), while review objects observed via the REST API carry `copilot-pull-request-reviewer[bot]` (widely reported id `175728472`; not verifiable from this sandbox because `api.github.com/users/*` is blocked here). Treat any Copilot identity as OBSERVE until confirmed on the live installation.

Grade: **PROVE** for `user.id`/`user.type`/`login` on a submitted review; **OBSERVE** for what kind of principal stands behind a Bot (see Part C).

### A2. Reviewer authority at approval time

Point-in-time authority is the central gap. The available signals:

1. **`GET /repos/{owner}/{repo}/collaborators/{username}/permission`** — App permission **`metadata` (read)** per the App mapping (`metadata` → `get-repository-permissions-for-a-user`). Returns `repository-collaborator-permission` with `permission` ("the legacy base roles of `admin`, `write`, `read`, and `none`, where the `maintain` role is mapped to `write` and the `triage` role is mapped to `read`"), `role_name` ("the name of the assigned role, including custom roles"), and `user` (a `collaborator` with `permissions.pull/triage/push/maintain/admin`). The OpenAPI text is explicit: "The calculated permissions are the highest role assigned to the collaborator after considering all sources of grants, including: repo, teams, organization, and enterprise. There is presently not a way to differentiate between an organization level grant and a repository level grant from this endpoint response." This is **current** permission only. Grade: **OBSERVE** (now), **NOT KNOW** (at approval time) unless the query is made at the moment of the `pull_request_review.submitted` webhook and stored — then it is PROVE-by-contemporaneous-observation, which the receipt must label as such.

2. **GraphQL `PullRequestReview.authorCanPushToRepository: Boolean!`** — "Indicates whether the author of this review has push access to the repository." Grade: **OBSERVE**.

3. **`author_association`** (REST enum `COLLABORATOR`, `CONTRIBUTOR`, `FIRST_TIMER`, `FIRST_TIME_CONTRIBUTOR`, `MANNEQUIN`, `MEMBER`, `NONE`, `OWNER`; GraphQL `CommentAuthorAssociation` same set). Computed at read time; not a permission level. Grade: **INFER** at best; never use it to claim write access.

4. **Team membership** — `GET /orgs/{org}/teams/{team_slug}/memberships/{username}` requires App permission **`members` (read)**. Grade: **OBSERVE** (current).

6. **Historical permission** — only the audit log records permission changes (`repo.add_member`, `team.add_repository`, `org.update_member`, etc.). `GET /orgs/{org}/audit-log` is **GHEC/Enterprise-only** in the OpenAPI (`ghec.json` has `/orgs/{org}/audit-log` and `/enterprises/{enterprise}/audit-log`; the `api.github.com` FPT description does not), and needs `organization_administration` read. Plan-gated. Grade: **NOT KNOW** on Free/Team; **OBSERVE (reconstructable)** on GHEC with the audit-log permission.

Receipt sentence when unavailable: *"NOT_PROVEN: reviewer authority is reported as of receipt time (`permission`=…, `role_name`=…), not as of the approval timestamp; GitHub does not expose historical permission under this installation."*

### A3. CODEOWNERS

- **`GET /repos/{owner}/{repo}/codeowners/errors`** (App permission **`contents` read**; optional `ref` query param "used to determine which version of the CODEOWNERS file to use") returns only syntax `errors[]` (`line`, `column`, `kind`, `source`, `suggestion`, `message`, `path`). It does **not** return owners for a path.
- There is **no REST or GraphQL field that returns the code owners for a given path or for a PR's files.** GraphQL `PullRequest.reviewRequests` returns `ReviewRequest{ requestedReviewer: RequestedReviewer (User|Team|Mannequin|Bot), asCodeOwner: Boolean! }` — `asCodeOwner` is the only platform-asserted CODEOWNERS signal, and it is present only for requests GitHub auto-created (and vanishes once the request is fulfilled/removed). `suggestedReviewers: [SuggestedReviewer]!` ("based on a user's commit history and review comments"; `isAuthor`, `isCommenter`, `reviewer`) is a heuristic, not CODEOWNERS.
- Ruleset `require_code_owner_review` (boolean in `repository-rule-pull-request.parameters`): "Require an approving review in pull requests that modify files that have a designated code owner." Docs: "if code has multiple owners, an approval from *any* of the code owners will be sufficient." Team owners must have explicit write access or "a code owner will not be assigned." Ruleset `required_reviewers` (beta: "A collection of reviewers and associated file patterns") is the newer path-based mechanism and is readable via `GET /repos/{owner}/{repo}/rulesets` (**`metadata` read**), but note the ruleset read hides `bypass_actors` (A7).
- **Local computation** is possible: fetch `CODEOWNERS` from `.github/`, root, or `docs/` on the *base* branch at the merge base/merge commit (**`contents` read**), apply gitignore-style patterns with "the last matching pattern takes the most precedence," resolve `@org/team` via `members` read, resolve write access via A2. Merge-Proof can then say which approvers *matched* the owner set. GitHub's own evaluation is not exposed; the rule-suite record (A7) reports only `rule_type`/`result`/`details` for the whole `pull_request` rule.

Grade: **OBSERVE** for `asCodeOwner` requests; **INFER** for locally computed matches; **NOT KNOW** for "GitHub judged the code-owner requirement satisfied by reviewer X". Receipt: *"NOT_PROVEN: GitHub does not expose which approval satisfied `require_code_owner_review`; Merge-Proof's local CODEOWNERS match is an inference."*

### A4. Approval ↔ head binding

- REST review `commit_id`: "A commit SHA for the review. If the commit object was garbage collected or forcibly deleted, then it no longer exists in Git and this value will be `null`." GraphQL `PullRequestReview.commit: Commit` (nullable) and `state: PullRequestReviewState!` (`APPROVED`, `CHANGES_REQUESTED`, `COMMENTED`, `DISMISSED`, `PENDING`), `submittedAt`. **PROVE**: "review R (APPROVED) was submitted against head commit C at T."
- Dismissal: REST `state: "DISMISSED"`; GraphQL timeline `ReviewDismissedEvent { actor, createdAt, dismissalMessage, previousReviewState: PullRequestReviewState!, pullRequestCommit, review }`; webhook `pull_request_review` action `dismissed` (docs autogenerated payload page; not re-verified from schema in this sandbox). Audit `pull_request_review.dismiss` (fields include `review_id`, `actor`, `actor_is_agent`, `actor_is_bot`). **PROVE** that a review was dismissed, by whom, and (from `pullRequestCommit`) at which head.
- `reviewDecision: PullRequestReviewDecision` (`APPROVED`, `CHANGES_REQUESTED`, `REVIEW_REQUIRED`) is GitHub's *current* net verdict — **OBSERVE**, and after merge it is frozen but was computed against rules that may since have changed.
- `latestReviews` = "A list of latest reviews per user associated with the pull request that are not also pending review"; `latestOpinionatedReviews` = "A list of latest reviews per user associated with the pull request" (with `writersOnly: Boolean` argument to restrict to authors with write access — this is the closest thing to "approvals that count").
- **`dismiss_stale_reviews_on_push`** ("New, reviewable commits pushed will dismiss previous pull request review approvals"): docs say GitHub "records the state of the diff at the point when a pull request is approved… If the diff changes from this state (for example, because a contributor pushes new changes to the pull request branch or clicks **Update branch**, or because a related pull request is merged into the target branch), the approving review is dismissed as stale." Community reports (#181705) show dismissal messages "stale because it was submitted before the merge base changed" even with no base commits, i.e. the diff-change test is GitHub-internal and not exposed.
- **`require_last_push_approval`** ("Whether the most recent reviewable push must be approved by someone other than the person who pushed it"): with this setting stale reviews are *not* dismissed; "the pull request remains approved as long as someone other than the person who made the most recent changes approves it." GitHub staff confirmed (community #37531, #41547) that an author's "Update branch" empty merge historically counted as a push requiring re-approval and that "the behavior… is the way it's intended to work." Which push is "reviewable" is not exposed by API.

Validity matrix for "approval on commit A, then push B":
| setting | approval on A after push B | provable by Merge-Proof |
|---|---|---|
| neither | still counts | PROVE it counted only if `reviewDecision`=APPROVED at merge (OBSERVE) and no `ReviewDismissedEvent`; INFER that A≠head |
| `dismiss_stale_reviews_on_push` | dismissed if GitHub judged the diff changed | PROVE dismissal happened (state DISMISSED); NOT KNOW why GitHub judged diff unchanged if not dismissed |
| `require_last_push_approval` | counts only if approver ≠ pusher of B and approval submitted after B | INFER pusher of B via A6; NOT KNOW GitHub's own "last reviewable push" attribution |

Receipt: *"Approval by U on commit A (review `commit_id`=A); the merged head was H≠A. NOT_PROVEN: GitHub does not expose whether this approval was counted toward the merge requirement."*

### A5. Bot / agent approvals

- A GitHub App with `pull_requests: write` can `POST /repos/{owner}/{repo}/pulls/{pull_number}/reviews` with `event: "APPROVE"`. It counts toward `required_approving_review_count` only if the installation has write access; Apps can also be bypass actors (`actor_type: "Integration"`).
- **Copilot approvals (public preview, changelog 2026-09-01 "Copilot code review can now approve pull requests")**: docs source `about-copilot-code-review` says "Every Copilot code review includes an approval assessment in the overview comment… On its own, this assessment does not count toward merge requirements. When approvals are enabled, Copilot can submit an approving review that satisfies your repository's required-approval rule the same way a teammate's approval would. If new commits are pushed after Copilot approves, the approval is dismissed, and you can re-request a review. Approvals are off by default and can be configured at the enterprise, organization, and repository levels. Repository administrators can also use file paths to control which Copilot approvals count toward merge requirements." Setting names (configure-code-review.md): repo "Allow Copilot to approve pull requests", "Allow Copilot approvals to count toward merge requirements", "File paths… Up to 15 globs"; org "Count Copilot approvals toward merge requirements"; enterprise "Allow Copilot to approve pull requests". The docs do **not** state the login/id of the approving review; treat it as the same Bot that posts Copilot reviews (OBSERVE, confirm on live data).
- **Unattributed Copilot PR extra approval** (available-rules-for-rulesets.md, `repo-rules-copilot-extra-approval`): "**Require an additional approval for unattributed Copilot pull requests** is enabled by default… When Copilot opens a pull request that isn't attributed to a person, the ruleset requires one more approval than the number you configured… If you clear this setting… If you also require an approval from someone other than the last person to push, at least one approval must cover the last push and come from someone other than Copilot." risks-and-mitigations.md adds this "always applies to branch protection rules" and that GitHub "Prevents the user who asked Copilot cloud agent to create a pull request from approving it." No REST/GraphQL field exposes whether GitHub applied the +1 or who it treated as the attributed person; the ruleset parameter name for this toggle does not appear in the OpenAPI `repository-rule-pull-request` schema (only `dismiss_stale_reviews_on_push`, `dismissal_restriction`, `require_code_owner_review`, `require_last_push_approval`, `required_approving_review_count`, `required_review_thread_resolution`, `required_reviewers`, `allowed_merge_methods`). Grade: **NOT KNOW**.

### A6. Author / pusher identity

- `PullRequest.author: Actor` / REST `pull_request.user` — the account that opened the PR. **PROVE** (identity of opener), but an opener is not necessarily the pusher or the code author.
- Commits: REST `GET /repos/{owner}/{repo}/pulls/{pull_number}/commits` (**`pull_requests` read**) gives `commit.author{name,email,date}`, `commit.committer`, `author`/`committer` (resolved GitHub users, nullable), `commit.verification{verified, reason, payload, signature, verified_at}`. GraphQL `Commit.author/committer: GitActor{ name, email, date, user }`, `authoredByCommitter`, `committedViaWeb`, `signature: GitSignature{ state: GitSignatureState, isValid, signer, wasSignedByGitHub }`. `reason` values (OpenAPI): `expired_key`, `not_signing_key`, `gpgverify_error`, `gpgverify_unavailable`, `unsigned`, `unknown_signature_type`, `no_user`, `unverified_email`, `bad_email`, `unknown_key`, `malformed_signature`, `invalid`, `valid`; GraphQL adds `BAD_CERT`, `OCSP_*`. Web-flow and Contents-API commits are GitHub-signed (`wasSignedByGitHub: true`).
- **Who pushed**: there is no per-push field on the PR. Signals: (a) `pull_request.synchronize` webhook `sender` (the account whose token performed the push) — only if Merge-Proof was receiving webhooks at the time; (b) GraphQL timeline `HeadRefForcePushedEvent { actor, beforeCommit, afterCommit, createdAt }` — force pushes only; ordinary pushes appear as `PullRequestCommit { commit }` with **no actor**; (c) **`GET /repos/{owner}/{repo}/activity`** (**`contents` read**) — "Lists a detailed history of changes to a repository, such as pushes, merges, force pushes… and associates these changes with commits and users"; fields `before`, `after`, `ref`, `timestamp`, `activity_type` (`push`, `force_push`, `branch_deletion`, `branch_creation`, `pr_merge`, `merge_queue_merge`), `actor` (nullable). Filter by `ref` and `actor`; `time_period` `day|week|month|quarter|year`. This is the best historical pusher source available to a read-only App, subject to retention (undocumented; the UI exposes up to a year via `time_period`) and to branches in forks (fork pushes are not in the base repo's activity). Grade: **PROVE** (pusher of `after` SHA on `ref`) when the activity row exists; else **NOT KNOW**.

Receipt: *"NOT_PROVEN: GitHub does not record the pushing account for non-force pushes in PR data; the repository activity log had no row for `after`=H under this installation."*

### A7. Bypass

- **Ruleset `bypass_actors`**: OpenAPI on `GET /repos/{owner}/{repo}/rulesets/{ruleset_id}`: "**Note:** To prevent leaking sensitive information, the `bypass_actors` property is only returned if the user making the API request has write access to the ruleset." `repository-ruleset-bypass-actor` = `actor_id` (nullable int; "Required for `Integration`, `RepositoryRole`, `Team`, and `User`… If `actor_type` is `OrganizationAdmin`, `actor_id` is ignored. If `actor_type` is `DeployKey`, this should be null"), `actor_type` enum `Integration`, `OrganizationAdmin`, `RepositoryRole`, `Team`, `DeployKey`, `User`; **`bypass_mode` enum `always`, `pull_request`, `exempt`** (default `always`) — "`pull_request` means that an actor can only bypass rules on pull requests… When `bypass_mode` is `exempt`, rules will not be run for that actor and a bypass audit entry will not be created." `exempt` therefore produces **no rule-suite record** — an `exempt` merge is invisible to A7's evidence trail. `current_user_can_bypass` (`always|pull_requests_only|never|exempt`) reflects the App's own status, not the merger's.
- **Rule suites** `GET /repos/{owner}/{repo}/rulesets/rule-suites` and `/{rule_suite_id}` — App permission **`administration` (read)**. List items: `id`, `actor_id`, `actor_name`, `before_sha` ("The first commit sha before the push evaluation"), `after_sha` ("The last commit sha in the push evaluation"), `ref`, `repository_id`, `repository_name`, `pushed_at`, `result` enum `pass|fail|bypass`, `evaluation_result` enum `pass|fail|bypass` (nullable). Detail adds `rule_evaluations[] { rule_source{type,id,name}, enforcement (active|evaluate|deleted ruleset), result (pass|fail), rule_type, details }`. Query params: `ref`, `time_period` enum **`hour`, `day`, `week`, `month`** (default `day`), `actor_name`, `rule_suite_result` (`pass|fail|bypass|all`), `evaluate_status`. A merge to a ruleset-protected branch produces a suite with `after_sha` = merge commit and `actor_name` = merger; `result: "bypass"` proves a bypass happened. Grade: **PROVE** (within ~30 days, with `administration` read); otherwise **NOT KNOW**.
- **Delegated bypass requests** exist only for **push rulesets** and **secret-scanning push protection**: GHEC OpenAPI paths `/repos/{owner}/{repo}/bypass-requests/push-rules[/{bypass_request_number}]`, `/orgs/{org}/bypass-requests/push-rules`, `/enterprises/{enterprise}/bypass-requests/push-rules`, and `…/bypass-requests/secret-scanning`. `push-rule-bypass-request` fields: `id`, `number`, `requester`, `request_type`, `data`, `resource_identifier`, `status`, `requester_comment`, **`expires_at`**, `created_at`, `responses[] { id, reviewer, status, created_at }`. No delegated bypass exists for branch (pull-request) rules; grants expire (`expires_at`); GHEC only.
- **Classic branch protection**: `GET /repos/{owner}/{repo}/branches/{branch}/protection/enforce_admins` → `protected-branch-admin-enforced { url, enabled }` (**`administration` read**). With `enabled: false` only the audit log records admin merges.
- GraphQL `PullRequest.viewerCanMergeAsAdmin: Boolean!` ("Indicates whether the viewer can bypass branch protections and merge the pull request immediately") is about the *viewer* (the App) — useless for the merger. `PullRequest.mergedBy: Actor` / REST `merged_by` **PROVE** who merged.
- **Audit log** (GHEC/enterprise): `protected_branch.policy_override` — "A branch protection requirement was overridden by a repository administrator." Fields: `actor`, `actor_id`, `user`, `user_id`, `actor_is_agent`, `actor_is_bot`, `after`, `before`, `branch`, `compliant_pull_request_ids`, `deploy_key_fingerprint`, `overridden_codes`, `reasons`, `referrer`, `rule_suite_id`, `topic`. `pull_request.merge` — fields `actor`, `actor_id`, `user`, `user_id`, `actor_is_agent`, `actor_is_bot`, `pull_request_id`, `pull_request_title`, `pull_request_url`, `topic`. `pull_request_review.submit`/`.dismiss` carry `review_id`. Plan-gated to GHEC (org audit log API needs `organization_administration` read; enterprise audit needs enterprise-level installation).
- **TTL**: `bypass_actors` never expire; delegated push bypass has `expires_at`; rule suites ≤ `month`; audit log 180 days (GHEC).

Receipt: *"NOT_PROVEN: the installation lacks `administration:read` (or the merge is older than the rule-suite window), so Merge-Proof cannot establish whether the merge used a bypass; ruleset `bypass_actors` are hidden from this installation."* Add: *"Actors with `bypass_mode: exempt` leave no bypass record; absence of a bypass record is not proof that no bypass occurred."*

### A8. Deployment gates

- `deployment_protection_rule` webhook (action `requested`; payload `environment`, `event`, `deployment_callback_url`, `deployment`, `pull_requests`) is delivered only to Apps installed as custom protection rules; callback via `POST {deployment_callback_url}` needs `deployments: write` — out of scope for read-only.
- `GET /repos/{owner}/{repo}/actions/runs/{run_id}/pending_deployments` (**`actions` read**) lists `environment`, `wait_timer`, `wait_timer_started_at`, `current_user_can_approve`, `reviewers[]`. Granted approvals: `GET …/runs/{run_id}/approvals` (`environments[]`, `state`, `user`, `comment`).
- Audit `workflows.bypass_protection_rules` (fields `run_number`, `workflow_run_id`, `actor`, `actor_is_bot`; no `actor_is_agent`) and `workflows.approve_workflow_job` (`workflow_run_id`, `run_number`, `actor_is_agent`).
Grade: **OBSERVE** (current run approvals); **NOT KNOW** for bypass without audit log.

## PART B — What did a `pull_request`-triggered Actions run actually test?

### B1. The run-level fields

`workflow-run` (REST `GET /repos/{owner}/{repo}/actions/runs/{run_id}`, **`actions` read**) properties: `id`, `name`, `node_id`, `check_suite_id`, `check_suite_node_id`, `head_branch`, `head_sha` ("The SHA of the head commit that points to the version of the workflow being run"), `path` ("The full path of the workflow", e.g. `octocat/octo-repo/.github/workflows/ci.yml@main`), `run_number`, `run_attempt` ("1 for first attempt and higher if the workflow was re-run"), `referenced_workflows`, `event`, `status`, `conclusion`, `workflow_id`, `pull_requests` ("Pull requests that are open with a `head_sha` or `head_branch` that matches the workflow run. **The returned pull requests do not necessarily indicate pull requests that triggered the run.**"), `created_at`, `updated_at`, `actor`, `triggering_actor`, `run_started_at`, `head_commit` (`nullable-simple-commit`: `id`, `tree_id`, `message`, `timestamp`, `author`, `committer`), `head_repository`, `display_title`, `previous_attempt_url`.

`pull_requests[]` items are `pull-request-minimal`: `id`, `number`, `url`, `head{ref, sha, repo{id,url,name}}`, `base{ref, sha, repo{id,url,name}}`.

**Is `pull_requests[].base.sha` the base at trigger time or the current tip? Neither reliably.** Evidence:
- The OpenAPI description says the array is a *lookup* of open PRs matching `head_sha`/`head_branch` — it is PR metadata joined at read time, not run metadata.
- Community #59677 (unanswered by staff): "`${{ github.event.pull_request.base.sha }}` … is the SHA of the base branch at the time the PR was created"; a contributor observed it "always corresponds to the SHA of the head/tip of the base branch at the moment of either creation of the PR or the last force-push." The same stored `base.sha` is what `pull_requests[].base.sha` surfaces.
- gitmoot/gitmoot#2103 measured six PRs with multiple runs each while `main` moved between runs: "`pull_requests[].base.sha` on a workflow run is PR-level and constant, not the base the run resolved against… that field cannot distinguish a run from before a base move from one after it."
- Conclusion: `pull_requests[].base.sha` is a **cached PR-level value** (typically the base tip when the PR was opened/last rebased), not the base used for the run's merge commit. Do not use it for "tested against base B".

`check-suite` (`GET /repos/{owner}/{repo}/check-suites/{id}`, **`checks` read**): `head_branch`, `head_sha` ("The SHA of the head commit that is being checked"), `before` (nullable), `after` (nullable), `pull_requests[]` (same `pull-request-minimal`), `app`, `head_commit`, `rerequestable`, `runs_rerequestable`. `before`/`after` are the head-branch push range, not the base. For **`pull_request` and `pull_request_target`** events `head_sha` is the PR head (`github.event.pull_request.head.sha`); for **`push`**, `head_sha` = tip pushed to the ref; for **`merge_group`**, `head_sha` = the SHA of the temporary merge-group commit on `gh-readonly-queue/{base}/pr-N-<sha>` (docs: temporary branches "contain a different `sha` from the pull request"), and `github.event.merge_group.{head_sha, base_sha, head_ref, base_ref}` are in the event payload — this is the one PR-CI event whose tested commit is a first-class field.

### B2. The tested commit: `GITHUB_SHA` vs API fields

Docs (events-that-trigger-workflows.md, `pull_request`): `GITHUB_SHA` = "Last merge commit on the `GITHUB_REF` branch", `GITHUB_REF` = `refs/pull/PULL_REQUEST_NUMBER/merge`; "Note that `GITHUB_SHA` for this event is the last merge commit of the pull request merge branch. If you want to get the commit ID for the last commit to the head branch of the pull request, use `github.event.pull_request.head.sha` instead." "Because `actions/checkout` uses `GITHUB_REF` by default, it checks out the merge branch. Your CI tests run against the merged result, not just the head branch alone." "Workflows will not run on `pull_request` activity if the pull request has a merge conflict." For `pull_request_target`: `GITHUB_SHA` = "Last commit on the PR base branch", `GITHUB_REF` = PR base branch (so a `pull_request_target` run tests nothing from the PR unless the workflow explicitly checks out the head). For `push`: "Tip commit pushed to the ref."

**Is the merge commit SHA (GITHUB_SHA) recoverable from any API field without job logs? No.** `workflow_run.head_sha` is the PR head (not the merge commit); `check_suite.head_sha` is the PR head; `pull_requests[].base.sha` is stale PR metadata; the `refs/pull/N/merge` ref is mutable and is regenerated (changelog 2026-02-19, "Changes to test merge commit generation for pull requests", quoted via search excerpt: test merge commits "will only be generated when… changes are pushed to the pull request branch, the merge base between the pull request and base branches changes, or the current test merge commit is older than 12 hours"; previously also on page view; "This change does not impact mergeability checks, reporting of merge conflicts, or rule enforcement"). So at receipt time the current `refs/pull/N/merge` is generally *not* the commit the run tested, and after merge the ref is dropped.

The only recovery path is the **job log**: `GET /repos/{owner}/{repo}/actions/jobs/{job_id}/logs` (**`actions` read**; "Gets a redirect URL to download a plain text file of logs for a workflow job. This link expires after 1 minute."; one call per job plus `GET …/runs/{run_id}/jobs` to enumerate; retention "By default, checks, workflow runs, commit statuses, and the artifacts and log files generated by workflows are retained for 90 days" (configurable 1–400 days on GHEC; 1–90 on public repos). In the checkout step, `actions/checkout` runs `git checkout --progress --force <ref>` (git-command-manager.ts) and git itself prints `HEAD is now at <short-sha> Merge <head-sha> into <base-sha>` — the GitHub-generated test merge commit's subject line embeds both parents. gitmoot#2103 confirms: "the checkout step log is the only source found… `HEAD is now at [commit] Merge [sha] into [base_sha]` … requires four API calls rather than two." Checkout also runs `git log -1 --format=%H` (non-silent) and sets the `commit` output. Caveats: only with default-`ref` checkout; log lines are runner output (INFER-grade), gone after retention.

### B3. Precisely what is provable

- **PROVE**: "Run R (`id`, `run_attempt`, `path`@ref, `event`) with conclusion C ran for head H (`head_sha`) and was created at `created_at`/`run_started_at`; it was triggered by `triggering_actor`." Also "check-run K (`head_sha`=H, `app.id`, `conclusion`, `completed_at`) exists."
- **NOT PROVE from API**: "Run R tested H merged onto base B." The merge parent B and the merge commit M are not in any REST/GraphQL field for `pull_request` runs.
- **INFER (with logs)**: from the checkout log line, M and B; then Merge-Proof can compare B to the base tip at merge time (`merge_commit_sha`'s first parent, from `GET /repos/{o}/{r}/commits/{merge_commit_sha}` → `parents[]`). If B ≠ first parent of the merge commit, the receipt must say the run tested a different integration than what was merged.
- **merge_group runs are the exception**: `merge_group.head_sha` is the exact commit that the queue later fast-forwards onto the base ("`activity_type: merge_queue_merge`" in repo activity), so "run R tested M and M was merged" is PROVE-grade when merge queue is used and `GET /repos/{o}/{r}/commits/{head_sha}` shows M is an ancestor of the base.
- **Actor fields**: `actor` vs `triggering_actor` — `actor` is the user whose identity the run uses (the PR head pusher for `pull_request`), `triggering_actor` is who caused *this attempt* (re-run clicker). For Copilot cloud-agent PRs, workflows do not run "until… a user with write access… clicks the **Approve and run workflows** button" (risks-and-mitigations.md; changelog 2026-03-13 added an admin opt-out), so `triggering_actor` on such runs is the approving human — a useful, platform-asserted signal.

## PART C — Agent provenance signals, reliability-ranked

Ranking: **platform-asserted** (GitHub computes it from the authenticating credential: `type`, `id`, `login`, `actor_is_agent`, `verification.verified`, `performed_via_github_app`); **vendor-asserted** (the vendor's system writes it under an identity it controls: trailers on commits signed by the vendor's App, `Agent-Logs-Url`); **self-asserted** (anyone with push can write it: git author/committer strings, unsigned trailers, PR body markers); **heuristic** (branch prefixes, wording).

Identities (ids from whycodes#113 and dev-common#245; `api.github.com/users/*` unreachable here — confirm on the live installation): `Copilot` → `167198135+Copilot[bot]`; `copilot-swe-agent[bot]` 198982749 (cloud agent commits; the PR author shows as "Copilot"); `copilot-pull-request-reviewer[bot]` 175728472 (reviews); `chatgpt-codex-connector[bot]` 199175422 and `openai-codex[bot]` 215057067; `claude[bot]` App id 209014114 / bot user 209825114; `cursor[bot]` 206951365; `google-labs-jules[bot]` 161369871; `devin-ai-integration[bot]` 158243242; `github-actions[bot]` 41898282.

Per-actor notes:
- **Human**: `type: "User"`, no suffix; commits verified only if signed (web-flow or user key). Agent authorship under a human identity is **NOT KNOW** unless a (self-asserted) trailer says so.
- **Copilot cloud agent**: platform-asserted: PR `user.login` = `Copilot` (Bot); commits "authored by Copilot, with the person who started the task listed as co-author… Commits are signed and appear as 'Verified'"; `Agent-Logs-Url` trailer (changelog 2026-03-20) links to the session; audit `actor_is_agent: true`, `agent_session_id`, `user` = initiating person (`actor:Copilot` filter, 180 days, enterprise); pushes only to a `copilot/` branch (heuristic) ; workflows gated by a human "Approve and run workflows" (→ `triggering_actor`). Automations are "attributed to the user who created the automation" — a human identity, agent-flagged only in audit.
- **Copilot code review / approval**: review `user` is the reviewer Bot (OBSERVE which login); approval `state: APPROVED` and is dismissed on new commits (documented). Whether it counted: NOT KNOW (setting not readable).
- **Codex (ChatGPT Codex Connector)**: App identity `chatgpt-codex-connector[bot]` on PR/commits when it pushes through the connector; commits created through the Contents API are GitHub-signed (`wasSignedByGitHub`), otherwise self-asserted. No documented trailer.
- **Claude**: `claude[bot]` App is the identity for claude-code-action pushes *when* the action authenticates as the App; the action's default `bot_id` is `41898282` (= `github-actions[bot]`) with `bot_name: claude[bot]`, so the git committer string can read `claude[bot] <41898282+claude[bot]@users.noreply.github.com>` while GitHub attributes on the numeric id — a mislabelled identity (dev-common#245). `use_commit_signing` (default `false`) makes commits GitHub-signed via the API. Trailers `Co-Authored-By: Claude …` and `Claude-Session: https://claude.ai/code/session_…` are emitted by Claude Code (observed in this session's own attribution instructions) — vendor-emitted but unsigned unless the commit is signed → self-asserted. A hidden "anthropic code agent" App was **not** found in any GitHub or Anthropic documentation reachable here; treat as unverified.
- **Devin / Cursor / Jules**: App bot identities on commits/PRs; Jules documents three authorship modes ("Jules as sole author (default), co-authored, or user only where Jules applies changes under the user's identity") — so a Jules change can appear as a plain human commit (NOT KNOW).
- **Generic GitHub App**: `type: "Bot"`, `<slug>[bot]`, `performed_via_github_app` on issue/timeline/deployment objects (schemas `issue-event`, `timeline-comment-event`, `review-dismissed-issue-event`, `deployment`, …; **not** on reviews or commits).
- **github-actions[bot]**: platform-asserted that a workflow with `GITHUB_TOKEN` acted; the workflow may have run any agent. `workflow_run.actor`/`triggering_actor` and the job log are the only clues.

**Can Merge-Proof say "pushed by an agent identity" vs "written by an agent"?** "Pushed/opened/reviewed by identity X (type Bot, id N)" is **PROVE**. "X is an AI agent" is **OBSERVE** by allow-list of known vendor bot ids (Bot type alone is not enough) and **PROVE** only where the enterprise audit log says `actor_is_agent: true`. "Written by an agent" is **NOT KNOW** in general: trailers, co-authors and PR-body markers are self-asserted unless carried inside a commit whose signature is `verified` under the vendor's App (then vendor-asserted).

**Does agent provenance change merge integrity?** GitHub's own rules say yes in two places: (1) the *unattributed Copilot PR* rule adds one required approval when the opener is an App identity not tied to a person, because "Requiring one approval usually means two people are involved… That assumption doesn't hold"; (2) "the user who asked Copilot… to create a pull request" cannot approve it. Merge-Proof should mirror this as an integrity dimension, not mere metadata: compute *distinct human principals* = {approvers with write, excluding the initiating human and any Bot} and report it alongside the raw approval count; flag when the PR author is `type: Bot` and the distinct-human count is < configured + 1; flag when the only APPROVED review is from a Bot. Vendor trailers stay metadata (recorded verbatim, labelled self-asserted).

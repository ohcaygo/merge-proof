## What an equivalent source must establish

A substitute must identify the complete applicable repository and inherited policy set; policy identity, enforcement and workflow-file targeting; allowed actor/event restrictions and enough actor-membership facts to evaluate them; observation/revision timing; and a fresh observation sufficient to detect a relevant change. Those facts must bind the exact evidence producer and candidate through the existing policy snapshot and per-claim currentness model. An unreadable parent, partial page, unknown actor membership or ambiguous revision cannot prove satisfaction or absence. GitHub observations retain `GITHUB_API` trust. An HMAC delivery authenticates transport to the receiver, not an independently verifiable statement signed by GitHub for a third party.

This is the same positive-evidence requirement used by the candidate. A successful workflow, a passing rollup, a cached export, a customer assertion that there are no policies, or silence in an event stream does not establish the missing policy facts.

## Read-default capability and customer presentation

The accepted direct comparison found `CI_EXECUTED:l3 signed queue validation` and `RULES_SNAPSHOT` UNKNOWN with Read; the result was NOT_PROVEN. Exact Git reconstruction, observed run/check/review/branch-rule data, independent claims, immutable history and portable historical verification remain available. `TARGET`, zero-review `APPROVAL_CURRENT`, and `REMOTE_DURABLE` remained TRUE in that fixture. This does **not** imply all authorization shapes pass with Read.

Fresh full VERIFIED/PROCEED cannot be claimed when a required execution-policy fact is unavailable. Coverage positivity would also depend on eligible producers, in addition to its separate missing aggregate adapter. Enabling an optional mode is never itself evidence that a claim passed. The invariant stays: sufficient current positive evidence → VERIFIED; insufficient/ambiguous/unavailable evidence → NOT_PROVEN; demonstrated unmet required condition → FAIL.

Proposed default UI text, adjacent to the existing claim/gap:

> Execution-policy proof unavailable. GitHub requires Administration: Write to read workflow execution protections. Merge-Proof uses Administration: Read by default. This claim remains NOT_PROVEN. Optional Enhanced Policy Proof can request the additional permission for selected repositories.

Proposed opt-in disclosure:

> Enhanced Policy Proof checks whether the evidence producer satisfied GitHub's applicable actor, event and workflow-file restrictions. GitHub grants repository administration write access for these reads. Merge-Proof will use it only to read execution policy, never to change repository administration. This is a powerful GitHub grant; the application's read-only use does not remove the authority from a compromised credential. Missing parent policies or other evidence can still leave a claim NOT_PROVEN.

These are reviewed design copy, **not deployed UI**. Receipt provenance includes the relevant policy observations/source and dependent claims, never the customer's entire configuration or credentials. Existing provider-trust labels, frozen replay and per-claim invalidation remain authoritative.

## Optional Enhanced Policy Proof design

GitHub permissions belong to an App registration and installations approve increases. Merely minting narrower tokens after changing the primary registration to Write does not preserve a Read-only installation request for new customers. [App permission updates](https://docs.github.com/en/apps/maintaining-github-apps/modifying-a-github-app-registration). Therefore the concrete proposed installation design is an **optional companion policy-reader App feeding the existing collector**, with the primary Merge-Proof App retaining Read. This is a credential boundary within the same proof service, not a governance/configuration subsystem. Registering that companion remains an owner decision; nothing was registered.

Implementation contract for the next candidate:

1. Persist an explicit per-customer/per-repository opt-in linked to immutable repository, account and both installation IDs. The companion requests only repository Administration Write plus GitHub's mandatory Metadata Read. It requests no organization permission. Selected repositories must be the intersection of the primary installation, companion installation and explicit opt-in. No automatic repository additions.
2. Keep primary `installationClient()` Read. Add a dedicated policy client seam used only by execution-policy discovery/detail reads. Do not replace the entire `ProofService.appClient` with a Write client as the private acceptance harness did. Mint a one-repository, short-lived policy token only after confirming the live grant and opt-in; isolate its credential from check publication, normal collectors and customer responses.
3. Enforce GET-only, HTTPS, exact `api.github.com` host and repository policy list/detail path allowlists, bounded same-route pagination and no redirects. Validate discovered self links before requesting them. Token issuance/revocation belongs to a separate fixed App authentication path. Reject every repository administration mutation locally before network I/O; log only method, scope, request ID and outcome, never secrets.
4. Do not follow inherited org/enterprise sources with broader credentials automatically. If repository authorization cannot read their required detail, preserve NOT_PROVEN with the precise source-access reason. Repository opt-in does not authorize organization Administration Write. Parent-scope support needs separate owner/security review and live acceptance.
5. Model mode status independently of verdict: off, approval pending, available, temporarily unavailable, revoked. Use fresh installation readback and actual successful policy preflight, not a consent click alone. An outage, 403, partial response or uninstall invalidates only dependent claims through existing currentness. Existing independent claims/history remain intact. No fallback to “no policy.”
6. On disable/revocation, discard/revoke active policy tokens, stop enhanced reads and reobserve dependent claims. Historical signed receipts remain immutable. Require access/entitlement checks for their retrieval. Relevant revision, normalized restrictions and producer binding use the existing receipt/provenance representation.
7. Before shipping: test default installation/token behavior, cross-tenant/repository rejection, grant pending/revoked/outage, blocked non-GET calls, malicious/foreign source links, pagination/parent gaps, actor/event and policy changes, same-name producer collisions, and unchanged historical replay. Then run the affected complete regressions/model/factory/reconstruction suites and a new exact-candidate live signed queue journey. The accepted `7953ecd` run does not validate this future credential integration.

**Status:** design complete for review; customer opt-in, dedicated policy client/credential routing, consent UI and their acceptance are unimplemented in `7953ecd`. This is stated as an implementation gap, not hidden behind the already accepted queue result.

## Coverage adapter boundary

`github/coverage.js` already defines the internal normalized evidence contract and numeric evaluator. `collect` deliberately leaves live aggregate evidence unavailable. A future adapter may populate that existing field only from a trustworthy provider observation with:

- Stable observation identity/time and authenticated provider provenance; exact repository ID, PR/head and provider-candidate commit/tree.
- Complete all-report integer covered/total line counts for that candidate, with an explicit completeness contract and no rounding into success.
- For every contributing producer: exact check ID, run ID/attempt, job ID, workflow ID/path/blob and event; each must uniquely match an eligible accepted execution in the existing evidence model. A same-name check, upload acknowledgment or success status is insufficient.
- For a maximum-drop rule: the bound default-branch ref/commit at observation, complete comparable counts and trustworthy baseline provenance. No unbound “latest coverage” baseline.
- Existing threshold/drop policy identity and relevant revisions, bound in `coverage.binding`, with producer, baseline and policy changes invalidating only dependent claims.

The adapter must validate source authenticity/completeness before setting AVAILABLE; it cannot infer completeness from a list of uploads. Retain only verdict-relevant raw references and normalized facts. Partial, missing, conflicting, unsupported or unavailable evidence stays NOT_PROVEN. A qualifying complete observation demonstrating a required threshold/drop violation yields FAIL. Sufficient current positive evidence can satisfy this claim; it does not bypass other required claims.

No alternative provider is falsely labeled `GITHUB_CODE_QUALITY`/`GITHUB_API`. A different trustworthy provider would need an explicit source contract and corresponding code/version validation, while preserving these verdict semantics. GitHub's rule configuration, findings, upload-processing state and rollups do not currently establish this aggregate/provenance boundary. See [the addendum's provider evidence and tests](capability-addendum.md). **The positive collection adapter remains unimplemented.** An eligible paid environment alone would not close that API gap.
